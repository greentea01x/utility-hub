Rooms & Tenants

Five screens hold the master data every other screen reads: the room a bill is addressed to, the area the common-area fee is computed from, the meter baselines the very first reading resolves against, and the tenant whose LINE account receives the message. Nothing here computes money, but every number here ends up on a receipt, so the screens are built around three rules the decision log makes non-negotiable: room status is derived from the tenant link and is never a field (D-07), baselines live on the room and are frozen the moment the room has a reading (D-06), and a LINE User ID is never typed by a human — it arrives through the six-character code flow (D-29).

How to read these screens

Every mockup is real HTML using only the tokens.css product classes, rendered at the surface it is designed for: the Admin desktop frame is ~1,000 px of a 1,280 px browser, the phone frame is 390 px. Numbered markers on the mockup match the list beneath it. All names, phone numbers and LINE display names are fictional seed values (D-44); room 205 carries the PRD §28 demo data verbatim.

Uniqueness is a database constraint, so the error can only be reported after submit (annotation 3 of the alternate frame).
  2. 2 ชั้น is entered, never parsed from the room code — a select of 1–5 seeded from the existing floors. Two features read this column directly: the floor grouping on จดมิเตอร์ and the floor audience on ประกาศ (D-47).
  3. 3 ประเภทห้อง is optional and display-only. The hint says so out loud, because a "type" field is exactly the kind of column somebody later tries to price against — and pricing per type is not in this product.
  4. 4 ขนาดพื้นที่, DECIMAL(6,2), admin only, audited on every change (ROOM_AREA_CHANGE). The hint shows the arithmetic it drives so the operator can sanity-check their own entry against a bill they have seen (D-09, D-38).
  5. 5 The baselines get their own card and their own explanation. This is the highest-consequence field pair on the screen: entered wrong, the room's first bill charges 1,260 units instead of 10. They are written to rooms, not to meter_readings, so nothing can collide with the room's first real reading (D-06).
  6. 6 No status control. The card explains the rule instead of offering a select; there is no way to make a room Occupied except by giving it an Active tenant (D-07).
  7. 7 บันทึก POSTs and, on success, redirects to the new room's detail page with a toast. On failure the same page re-renders with every typed value preserved — never a redirect, never a lost form (D-40).

6. Assumptions recorded by these screens

  1. Form routes. The Design Foundations site map counts fifteen navigable pages and the ADR's views/pages/ list names rooms.ejs, room-detail.ejs and tenants.ejs. The four form and detail surfaces here — /rooms/new, /rooms/:id/edit, /tenants/new, /tenants/:id, plus /tenants/:id/edit — are treated as form modes of those same templates, not new page files, and every mutation is an ordinary form POST with POST-Redirect-GET. No new JSON endpoint is introduced: the ADR fixes the API at exactly seven, and an eighth is a decision, not a convenience.
  2. Room 205's meter baselines. D-44 requires twelve periods of history, so room 205's opening values are shown as baseline_water 1,143 and baseline_electric 4,559 at 30 ก.ย. 2025 — the only values from which twelve months of realistic consumption land exactly on the PRD §28 demo (1,250 → 1,260 and 5,280 → 5,350). The engineering data model's worked example uses 1,192 / 5,215 for a deliberately minimal two-period extract; both reproduce the binding demo arithmetic, and neither is an expected value in any test.
  3. Tenant name for room 205. สมชาย ใจดี, matching the seed in the engineering data model and API spec. Design Foundations §8.7 prints a different name on its receipt sample; the seed value is the one used here and in every table that names room 205's tenant.
  4. Room codes and ids. The URL bar shows /rooms/205 and /tenants/2050, following the data model's seed ids. The room code is the only room identifier a human ever reads; the surrogate id appears nowhere on screen.
  5. Uniform 30.00 ตร.ม. Every room in the list carries the same area and type because D-44 seeds a uniform studio block — that is what makes PRD §16's 70,350.00 = 67 × 30 × 35 come out exactly. It is a seed property, not a product constraint: the area field is per-room and free.
  6. Fictional data. All tenant names, phone numbers, LINE display names and the link code K7QM9X are invented for the mockups. Amounts other than room 205's 180 / 560 / 1,050 / 1,790 are illustrative and are never expected values in a test (D-44).
  7. Row actions on the tenants list. ยกเลิกการผูก is rendered as a plain POST with a toast rather than a confirmation dialog, because D-39 fixes the dialog at exactly six call sites and unlinking destroys nothing that a new code cannot restore.
