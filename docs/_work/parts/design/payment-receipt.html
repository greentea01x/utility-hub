Payment & Receipt

Three screens close the money loop of the product: the counter takes cash against exactly one Unpaid bill, the receipt is issued and printed on A5, and every settled payment stays findable and reprintable afterwards. Together they implement PRD §12, §13 and §18 functions 22–25, under the decisions that govern them — D-24 (full payment only, amount never an input), D-25 (void, never delete), D-26 (the database is the guarantee, not the button), D-27 (receipt fields and numbering), D-28 (A5 through the browser's own print dialog), D-39 (two of the six confirmation dialogs live here) and D-40 (empty, loading, error and 403 treatments).

The counter is Admin, not Staff

PRD §12 says เจ้าหน้าที่กด Confirm Cash Payment. That sentence contradicts PRD §4, which grants รับชำระเงิน and ออกใบเสร็จ to Admin only, and it is treated as a drafting error (D-36). Every screen in this section is Admin-only; a staff session reaching any of these routes gets the Thai 403 page, and no amount appears anywhere in a staff API response.

What the mockups are, and are not

All figures are the PRD §28 demo values (room 205, 30 ตร.ม., 10 หน่วย × 18, 70 หน่วย × 8, 30 × 35, total 1,790 THB, due 5 Sep 2026, paid 3 Sep 2026, receipt REC-202609-000852) and the D-44 seed identities. The calendar dates are documentation values: the live demo reproduces the arithmetic against dates computed from the run date, never this calendar (D-44). Tenant names, phone numbers and the apartment address are fictional.

ระบบจะออกใบเสร็จและส่งข้อความยืนยันผ่าน LINE ให้อัตโนมัติ
  1. 1Search field. A plain GET /payments?q=; Enter or ค้นหา submits. The server matches room_code by prefix and the active tenant's name by substring, and returns rooms of either status — a Vacant room can still hold an Unpaid bill left by a finished tenancy (D-07, D-08). One match renders the room directly; several render a chooser list; none renders the empty state (never a blank page, D-40). The query stays in the URL so the browser Back button returns the cashier to the same room.
  2. 2Room identity panel. Room code, floor, area and the room's current Active tenant. It is here so that a cashier who typed 250 instead of 205 reads the wrong tenant's name before money changes hands. Read-only; nothing on this panel is editable from the counter.
  3. 3LINE binding badge. ผูก LINE แล้ว or ไม่มี LINE, from the tenant's binding (D-29). Informational only: it predicts whether the ✅ confirmation message can be delivered after the payment (D-30). It never blocks or delays taking cash.
  4. 4Open bills list. Every bill of this room whose stored status is Unpaid, oldest period first. Draft bills never appear (they have not been approved and were never sent to the tenant) and Paid bills never appear. The status cell runs through the shared display helper, so a bill past its due date reads เกินกำหนด with data-status="Overdue" and no stored value changes (D-21).
  5. 5Bill selection. One radio, one bill — no multi-select, no "pay everything". Selecting a row applies tr.is-selected and rewrites the panel on the right; nothing is submitted yet. Every row shows its billing period because a room in arrears has several open bills, and paying the wrong month is precisely the mistake the void path exists to undo (D-25, D-39 #3).
  6. 6Frozen breakdown. Units, unit prices and line amounts are snapshots taken at Approve & Send and are not recomputed at the counter; no field here is editable through any endpoint (D-22). The three lines are always present, even at zero units, so the panel always sums to the total (D-41).
  7. 7ยอดที่ต้องชำระ — text, not an input. The stored payment amount is fixed at the bill total. Partial payment and overpayment do not exist in v1: a tenant who is short returns with the full amount and the bill stays รอชำระ / เกินกำหนด (D-24, D-05 #2). This is what lets Paid always mean "paid in full" without a fifth status.
  8. 8รับเงิน / เงินทอน cashier aid. Browser-side only (public/js/payment-change.js), recomputed on every keystroke. Non-numeric characters are ignored; a value below the total hides the change figure and shows รับเงินน้อยกว่ายอดที่ต้องชำระ as a hint but never disables the confirm button, because a cashier may skip the aid entirely. Neither value is submitted, stored, printed on the receipt or sent to LINE (D-24).
  9. 9ผู้รับเงิน and timestamp. Server-supplied and read-only (dashed border = system value): the signed-in Admin's ชื่อที่แสดง (D-46) and the server clock in Asia/Bangkok, 24-hour with the น. suffix (D-03). They are displayed because both are printed on the receipt.
  10. 10ยืนยันรับเงินสด — the one page action. Disabled while no bill is selected. It opens the confirmation dialog (marker 12) rather than posting immediately. On submit it takes .is-loading and disabled — a courtesy, never the guarantee: the guarantee is UNIQUE(active_bill_id) plus a conditional status update in the database (D-26). Resulting state on success: one payments row, bill Unpaid → Paid, one receipt number allocated, one LINE message queued, one audit row — one transaction, then a redirect to the receipt.
  11. 11Recent payments. The room's last settled bills with their receipt numbers, each linking to /receipts/:id. It answers "เดือนที่แล้วจ่ายหรือยัง" at the counter without leaving the screen, and it is the reprint path for a tenant who lost last month's slip.

  1. 1Success banner. Rendered once after the redirect from the payment POST and carries the three things the cashier must read back to the tenant: room, period and receipt number. A full result screen rather than a toast, because money moved and a LINE message was queued (D-40).
  2. 2Receipt number. REC-<payment month YYYYMM>-<6-digit sequence>, allocated inside the payment transaction from one counter that never resets (D-27).   3. 3Payment facts. Amount, method (เงินสด — the only method that exists in v1), the Admin who took it and the server timestamp. The bill's badge is ชำระแล้ว with data-status="Paid"; because the payment amount always equals the bill total, Paid needs no qualifier (D-24).
  4. 4LINE delivery state. Read from this bill's notifications row: ส่งแล้ว (ok), ยังไม่ได้ส่ง — ไม่มี LINE (neutral), ส่งไม่สำเร็จ (bad, error text on hover). In the latter two a ส่งข้อความอีกครั้ง button appears; the manual resend is never capped, unlike the three automatic attempts (D-30). Delivery state never affects the money state.
  5. 5พิมพ์ใบเสร็จ. POSTs /api/receipts/:id/print to increment print_count, then calls window.print(); the browser's own dialog handles paper and printer (D-28). After the first press the label becomes พิมพ์สำเนา and every later render carries the สำเนา mark. Printing from the browser's menu bypasses the counter and yields an unmarked copy — a listed limitation, not a defect (D-05 #11).
  6. 6Print counter. The only thing that decides whether the sheet coming out is an original or a copy. It is shown in plain words so the office can see the state before pressing, and it is why the copy mark is testable at all (D-27).
  7. 7A5 preview. The same markup the print route renders — what is on screen is what comes out of the printer. On screen the sheet is shown at its natural width without the full 200 mm page height; the print output is the complete A5 page shown below (D-28).
  8. 8ยกเลิกการชำระเงิน. Admin only, styled destructive and placed away from the print button. Opens dialog #5 of D-39, which insists the cash goes back across the counter first.   9. 9กลับไปหน้ารับชำระเงิน. Returns to /payments with the room still in the query, so the next tenant in the queue is one search away. The counter's normal loop is search → confirm → print → back.

On confirm, in one transaction: the payment row is marked voided (never deleted), the receipt row is marked voided and keeps its number, the bill returns to Unpaid — displaying as เกินกำหนด automatically if the due date has passed (D-21) — and an audit row is written. No LINE message is sent on the void; the office explains in person. The bill is then excluded from automatic reminders and carries the badge ระงับการแจ้งเตือนอัตโนมัติ, so the system never chases a tenant who paid and did nothing wrong (D-25).

Print layout — ใบเสร็จรับเงิน, A5 portrait

One route serves both the screen view above and the paper: window.print() with @page { size: A5 portrait; margin: 10mm } and a print stylesheet that hides the app chrome. No PDF library, no server-side rendering, no thermal-printer layout, no printer-driver assumptions (D-28). Fitting on exactly one A5 page with all three line items, the total and the number is a QA check.

  2. Payment search matches a room code by prefix and a tenant name by substring, across rooms of both statuses. A Vacant room can still hold an Unpaid bill from a finished tenancy (D-07, D-08), so restricting the search to Occupied rooms would hide money owed.
  3. History is filtered by payment date, the Dashboard tile by billing period. Both are correct and they will differ whenever a bill is settled in a later month; the รอบบิล column exists so the difference is visible rather than mysterious (D-41).
  4. If POST /api/receipts/:id/print fails, printing proceeds anyway with a warning. D-27 fixes the order (increment, then print) but not the failure path. The tenant is at the counter; blocking the print would be worse than an unmarked sheet, which is already an accepted outcome when printing from the browser menu (D-05 #11).
  5. The รับเงิน cashier aid never blocks the confirm button. A value below the total shows a hint only. The aid is optional scratch arithmetic, and D-24 states plainly that neither value reaches the API.
  6. Receipt routes are keyed by the receipt's row id, not its number (/receipts/1042 renders REC-202609-000852). The number is a document identifier that must survive voiding; the id is the route key.
  7. The receipt preview on the view screen is shown at natural width without the full 200 mm page height. The printed sheet is the A5 page shown in the print frame; the preview is a legibility aid, not a page-fidelity proof — that is a QA check on the real print output (D-28).
