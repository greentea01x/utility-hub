LINE Official Account Messages (Tenant)

The tenant is the only user of this product who never sees a screen we build. Everything a tenant receives arrives in one LINE chat with the apartment's Official Account, and everything a tenant does happens at the office counter with cash. This section specifies that chat: the six outbound message types, the account-linking conversation that makes them deliverable at all, the exact Thai text of each one, and what the office sees when a message does not arrive.

Binding constraints this section obeys
  • Plain text only (D-31). Seven templates, no Flex Messages, no images, no rich menu, no buttons inside a message. Every mockup below uses .bubble.oa; .flex-card and .rich-menu exist in tokens.css for a post-v1 version and a v1 mockup that uses them is a defect.
  • Braced placeholders are the template; the rendered text is an example. Each screen shows the D-31 template verbatim and then one worked example rendered with the PRD §28 values — room 205, 10 หน่วย × 18, 70 หน่วย × 8, 30 ตร.ม. × 35, ยอดรวม 1,790 บาท, ครบกำหนด 5 กันยายน 2026, ชำระ 3 กันยายน 2026, REC-202609-000852.
  • Money and dates (D-03). LINE messages write the number followed by บาท with the trailing .00 dropped (1,790 บาท), full Thai month names (5 กันยายน 2026), Gregorian years, 24-hour times with the suffix น., timezone Asia/Bangkok.
  • No product branding (D-01). The tenant sees the apartment's Official Account. The OA display name is apartment_name from Settings — ศุภาลัย เรสซิเดนซ์ in the seed — and the only signature that ever appears is — นิติบุคคล {apartment_name} on an announcement.
  • The OA is not a chatbot (D-29). Exactly three inbound behaviours exist: a string shaped like a link code, anything else, and the follow event. There is no menu, no query, no balance lookup, no tenant-facing web login (D-05, limitation 7).

How to read these screens

A LINE message has no interface states of its own — it is one immutable bubble in a chat we do not own. The five states every screen in this document set must specify therefore map onto delivery state, which is what the office can actually see and act on. The mapping below is the same on every screen, so each screen's table only fills in what is specific to that message.

Two things the mockups deliberately do not show

There is no read receipt we control and no delivery receipt LINE gives us. The อ่านแล้ว marks in the frames below are LINE client chrome drawn for realism only — the product never reads them, never stores them, and no screen, report or test case may claim a message was read. Likewise the input bar is the tenant's own keyboard: the product cannot pre-fill it, disable it, or attach a button to it.

  1. 1Chat header. The OA display name is settings.apartment_name (D-01) — never "Juristic Platform", never a product logo. The avatar and the Official badge are LINE's own chrome, configured once in the LINE Official Account Manager. Nothing here is rendered by our code.
  2. 2The BILL bubble. One plain-text message, sent after the approve transaction commits, never inside it (D-30) — a LINE outage cannot roll back an approval. The three item lines repeat the arithmetic rather than only the amounts, because the tenant's first question is always "why is it this much"; the numbers come from the frozen bill_items snapshot, so the message can never disagree with the printed bill or the receipt (D-17, D-22).
  3. 3Timestamp. Set by LINE at delivery, not by us. On a bulk approval of 64 rooms the drain loop spreads sends over up to three minutes, so timestamps across rooms differ by minutes — this is expected and is not a defect (D-19, D-45).
  4. 4The tenant replies. Nothing in the product asks for a reply, but tenants reply anyway. The inbound message is stored nowhere except LINE; it never reaches a staff screen, and no member of staff is notified.
  5. 5Fixed auto-reply. Any inbound text that is not shaped like a link code gets one fixed reply pointing at the office, sent with the Reply API on the event's reply token — it writes no notifications row and does not consume the 500-message allowance (D-29, ADR ENG-4). Full wording and the shape rule are specified in LM-6.
  6. 6Input bar. The tenant's own keyboard. v1 attaches no rich menu, no quick reply and no postback button (D-31), so this bar is the only inbound channel and it is used for exactly one thing: the six-character link code.

LM-8 · Deferred surfaces and assumptions recorded by this screen set

No rich menu and no Flex card in v1

The brief for this section asked for a rich menu "if the decisions include one" and for the bill to be a Flex card. D-31 excludes both: seven plain-text templates, no Flex Messages, no images, no rich menu. tokens.css carries .flex-card and .rich-menu for a post-v1 version and marks them reserved; a v1 mockup using either is a defect, so neither appears above and no rich-menu mockup was produced. What it would take to add one later: a rich menu is an image plus a tappable-area map uploaded to the LINE channel, so it needs a designed 2500×1686 asset the team does not have, and every cell must lead somewhere — and there is nowhere for a tenant to go, because there is no tenant-facing web surface (D-05, limitation 7). A Flex bill would additionally duplicate every amount in a second, richer format that must stay in step with the plain-text one; one template module, one string per message, is the decision (D-31).

  1. A-1 · Overdue uses the demo bill's counterfactual branch. Room 205's bill is paid on 3 กันยายน 2026, so it can never be overdue. LM-3 shows the same bill on the branch where the tenant does not come to the counter, which keeps the §28 figures exact rather than inventing a second room with invented amounts. The overdue dates (6, 13 and 20 กันยายน 2026) follow from due_date = 5 กันยายน 2026 and days_overdue IN (1, 8, 15).
  2. A-2 · PRD §15's overdue line is a summary, not the sent text. ⚠️ คุณมียอดค้างชำระ 1,790 บาท is reproduced in the copy table as documentation. The string actually sent is D-31 #4, which adds the room, the due date and the day count — a tenant renting two rooms cannot act on the short form, and D-31 is binding on exact wording.
  3. A-3 · Timestamps and battery levels in the frames are illustrative, except 09:00 น. on PRE_DUE and OVERDUE, which is fixed by D-32 and must not be redrawn at another hour. Bill and payment times follow the demo narrative (approved 1 ก.ย. 09:12, paid 3 ก.ย. 14:30) and match the receipt mockup in the foundations document.
  4. A-4 · Three strings are set here because no decision fixed them. The LINE greeting message (configured in the LINE Official Account Manager, not in code), the fixed auto-reply text that D-29 requires but does not word, and the code-shape rule that separates a code attempt from ordinary chat: trim, uppercase, then ^[A-Z2-9]{6}$ — a match that is not a live code gets LINK_FAIL, anything else gets the auto-reply. If engineering words any of the three differently, the template module wins and this table follows it.
  5. A-5 · Duplicate announcements for a shared LINE account are accepted, not fixed. LM-5's right-hand frame is real behaviour, not a mockup error. It follows from one notifications row per recipient tenant (D-30) combined with a per-tenant binding (D-29), and collapsing it would break the delivery counts that make ส่งบิลผ่าน LINE OA verifiable. It belongs in the Limitations list of any document that carries one.
  6. A-6 · The link-code slip is not mocked up here. It is a print artefact owned by the Tenants screen; this section specifies only its heading text and the code alphabet, so the two documents cannot drift into two different slips.
  7. A-7 · LINE test mode is ON in every environment (D-34), so during development and rehearsal every message in this section is redirected to one whitelisted userId while the intended recipient is still recorded on the row. The frames above show what the real tenant would see with test mode off — the state that exists only during the graded demo run.
  8. A-8 · Read receipts, day separators, the input bar, the avatar and the Official badge are LINE client chrome, drawn for realism. The product neither controls nor reads any of them, and no requirement, report or test case may depend on them. Where an earlier message is drawn dimmed it is a reading aid in this document only — it marks the context bubble so the eye lands on the new one; LINE renders every message at full strength.
