Meter Reading (Staff, mobile)

Meter Reading (จดมิเตอร์, route /readings) is the only screen a Staff account uses to do real work, and it is the only screen in the product designed phone-first. Everything on these four screens is derived from four binding decisions: the round mechanics (D-15), the reading row and its edit window (D-12), the below-previous block and the meter-replacement branch (D-13), and the Staff permission boundary (D-36).

Binding constraints these screens obey
  • D-36 — no money on the Staff surface. Staff never see a rate, an amount or a bill total; the figures are absent from the API response, not merely hidden by CSS. The live calculation Staff see is units only (10 หน่วย, 70 หน่วย). The 180 / 560 / 1,050 / 1,790 THB preview exists on the same route for an Admin session and is shown here as a clearly labelled variant frame.
  • D-15 — per-room save. One card per room, one บันทึก button per card, one request per room. A room counts as จดแล้ว only when both water and electricity are stored for the period. Four filter chips, default ยังไม่จด. Rooms grouped by rooms.floor under a sticky floor header, ordered by room code.
  • D-13 — hard block, not a rollover guess. There is no automatic rollover detection. A current reading below the previous one is a hard block with Save disabled; a rolled dial or a swapped meter is entered through the explicit เปลี่ยนมิเตอร์ในรอบนี้ branch, which both roles may use because Staff are the ones standing at the meter.
  • D-11 / D-12 — no period lock, no submitted state. Nothing is ever "closed". A reading is editable exactly while its room's bill for that period is Draft or does not yet exist, and frozen the moment the bill is approved: บิลอนุมัติแล้ว แก้ไขไม่ได้. The only way back is Admin reverting the bill to ฉบับร่าง (D-22).
  • D-18 — one submit button. ส่งให้นิติตรวจสอบ runs bill generation for the period. It is not one of the six confirmation dialogs in D-39, so the review screen is its confirmation step.

🏠ภาพรวม 🚪ห้องพัก 🔢จดมิเตอร์
  1. 1Month picker — defaults to the current calendar month in Asia/Bangkok and is displayed as "กันยายน 2026" (D-03); the value on the wire is the period key 2026-09. The arrows step one month and reload the page with ?period=. There is no open/close state and no lock (D-11): stepping back to สิงหาคม 2026 shows that month's rooms, editable only where the bill is still ฉบับร่าง or absent.
  2. 2Search — filters the visible list client-side on room code and tenant name; it does not change the chip counts or the X/Y counter, which always describe the whole period. Clearing it restores the active chip's full list. 44 px tall, 16 px text, so iOS does not zoom the page on focus.
  3. 3Filter chips (D-15) — ทั้งหมด / ยังไม่จด / จดแล้ว / ห้องว่าง, defaulting to ยังไม่จด because that is the working set of a round. The first three cover billable rooms only, so 67 = 25 + 42; ห้องว่าง lists the 13 vacant rooms with the badge ไม่ออกบิล for a voluntary reading (D-07) and never enters the counter. Selecting a chip re-renders the list without losing typed, unsaved values in a card that stays visible.
  4. 4Round progress — "จดแล้ว 42/67 ห้อง". A room counts as จดแล้ว only when both water and electricity are stored for the period (D-15). The value is recomputed from the server's response after every per-room save, never incremented client-side, so a failed save can never inflate it. The bar turns green at 67/67, the state the ≤ 15 min acceptance target in D-45 is measured against.
  5. 5Sticky floor header — groups come from rooms.floor, a real column, never parsed from the room code (D-47), and rooms are ordered by room code inside a group. The header stays pinned while the floor scrolls, so the walker always knows which floor the card on screen belongs to.
  6. 6Room card — one card per room holding Previous (read-only) and Current for both utilities plus its own บันทึก button, saved alone through one POST /api/readings (D-15). Nothing else on the page is submitted with it, so losing signal in a stairwell loses at most the room being typed.
  7. 7Live units — current − previous, recomputed on every keystroke, integer only. Units are the only derived figure a Staff session sees: no rate, no amount, no total (D-36). Previous is read-only text resolved by D-14 (the greatest earlier period for that room and utility, otherwise the room's baseline); the hint line names the source period so a catch-up entry after a skipped month is explained rather than disputed.
  8. 8Sticky round bar — carries the counter and the single page action ส่งให้นิติตรวจสอบ, which is enabled as soon as one room in the period has both readings (D-18). It opens the review screen (§3); it never posts directly, because the review screen is this action's confirmation step. The bar sits above the tab bar, so neither ever covers the other.

Alternate state — round complete, filter ทั้งหมด. Saved rooms collapse to a จดแล้ว summary row (D-15) with an แก้ไข affordance that re-expands the card while the bill is still ฉบับร่าง or absent.

The hint names the source period. When it is not the immediately preceding month the hint reads ครอบคลุมการใช้ตั้งแต่รอบ มิ.ย. 2026; when it is the room's opening value it reads ค่าเริ่มต้นของห้อง. Staff can never edit it — baselines are Admin-only and only before the room's first reading exists.
  3. 3Current reading input — 44 px tall, 16 px text, inputmode="numeric" so Android raises the numeric keypad (D-45). INT UNSIGNED, whole units only (D-16): a decimal point, a minus sign and any non-digit are rejected on input, and the server re-validates with zod. The field shows raw digits (1260) while every read-only figure on the page is formatted with a thousands separator (1,250) — a separator inside a numeric field fights the keypad.
  4. 4Live units — 5,350 − 5,280 = 70, recomputed on every keystroke and cleared to — while the field is empty. Units, not money: the Staff API response contains no rate and no amount (D-36).
  5. 5เปลี่ยนมิเตอร์ในรอบนี้ — available to both roles because Staff are the ones at the meter (D-13). Ticking it reveals the replacement branch (alternate B) and suspends the below-previous block. There is deliberately no automatic rollover detection: a dial that has rolled past its maximum is entered here, with the old meter's final number and the new meter's start number, so the arithmetic is recorded rather than guessed.
  6. 6บันทึก — saves this room alone through one POST /api/readings carrying both utilities, and returns the room's saved state plus the round's X/Y counter (D-15). The write is an UPSERT on UNIQUE(room_id, period, utility_type), so a double tap is a no-op rather than a duplicate (D-12); the button shows .btn.is-loading and is disabled for the duration. Saving recalculates that room's Draft bill in place immediately (D-18).
  7. 7Reading history — the three most recent periods for this room, units only. It is what lets a walker sanity-check a reading on the spot and is the same data D-13's soft usage flag is computed from. A missed month appears as a gap, never as a zero row (D-14).

  1. 8Inline failure banner — a failed save never redirects and never reloads the phone screen; every typed value survives (D-40). The banner summarises how many rows were refused and points at the one legitimate escape hatch, the meter-replacement checkbox.
  2. 9Below-previous hard block — the exact Thai string is เลขมิเตอร์ปัจจุบันน้อยกว่าเดือนก่อน (1,250) กรุณาตรวจสอบ, identical in the form and in the API envelope (error code READING_BELOW_PREVIOUS, HTTP 422) so one string is testable on both surfaces. The field takes .field.invalid and aria-invalid="true"; the units read-out clears rather than showing a negative, and CHECK (units >= 0) in the schema is the last word. The electricity field beside it shows the empty-field message กรุณากรอกเลขมิเตอร์: both utilities are required, because a room is only จดแล้ว with both.
  3. 10The escape hatch stays visible — the checkbox is not hidden behind the error. Ticking it clears the block for this room immediately and re-validates against the replacement rules instead.
  4. 11Save disabled — while any field on the card is invalid the button is .is-disabled. This is presentation only: the API rejects the same payload with 422 for every role, so a disabled button is never the security boundary.
  5. 12Checkbox ticked — reveals three required fields and switches the validation rules. Unticking it hides them, discards their values and restores the below-previous block.
  6. 13Mode warning — states plainly that the ordinary guard is off, so nobody uses this branch to force a bad number through. The row will carry meter_replaced = 1 and be flagged for Admin at the approval gate that already exists.
  7. 14Replacement fields — เลขสุดท้ายของมิเตอร์เดิม (old_final) and เลขเริ่มต้นของมิเตอร์ใหม่ (new_start, defaulting to 0). Validation: old_final ≥ previous_reading — เลขสุดท้ายของมิเตอร์เดิมต้องไม่น้อยกว่า 1,830 — and current_reading ≥ new_start — เลขปัจจุบันต้องไม่น้อยกว่าเลขเริ่มต้นของมิเตอร์ใหม่ (0). Both keep units ≥ 0.
  8. 15Reason, required — free Thai text stored on the reading row and written to audit_log with action METER_REPLACEMENT and the entering user's name (D-38). Empty reason blocks the save with กรุณาระบุเหตุผลการเปลี่ยนมิเตอร์.

This is the same expression the service computes; the screen never sends a units value.

Assumptions recorded for these screens

Design decisions taken here that the PM log does not settle
  1. Amounts are absent from every Staff frame. The brief for this section asked for live computed units and amounts on the reading screen; D-36 forbids Staff any amount or rate. D-36 wins. Units are live on the Staff screens, and the 180 / 560 / 1,050 / 1,790 preview is shown once, in a clearly labelled Admin frame on the same route.
  2. No rollover confirmation dialog exists. The brief mentioned a "rollover/replacement confirm"; D-13 states there is no automatic rollover detection and no dialog — a rolled dial is entered through เปลี่ยนมิเตอร์ในรอบนี้. The checkbox branch is the whole mechanism.
  3. Deep-link shape /readings?period=YYYY-MM&room=205. D-23 requires room codes that link "straight to the Meter Reading page for that room" but names no URL. A query parameter on the existing route keeps the ADR's seven-endpoint and route conventions intact and adds no page.
  4. Review screen shape ?view=review. D-18 places ส่งให้นิติตรวจสอบ on the Meter Reading page and D-39 gives it no dialog, so the review step is a mode of the same route rather than a new page, a new endpoint or a modal.
  5. Staff-side surfacing of a returned bill. D-22 defines the Admin revert and its mandatory reason but does not say how Staff learn about it. The banner and the per-card reason are derived from the existing audit_log BILL_REVERT row (D-38) — no new column, no notification table, no push.
  6. Three tabs, logout in the top bar. D-36 grants Staff exactly three pages; a fourth "account" tab would be a destination that is not one of them.
  7. Numeric inputs hold raw digits. Read-only figures use the D-03 thousands separator (1,250); the editable Current field shows 1260, because a separator inside a field driven by the Android numeric keypad has to be stripped on every keystroke.
  8. Reading history is capped at three periods on the phone. The room's full history lives on ห้องพัก → room detail; three rows are what fits above the fold and what a sanity check needs.
