Login & Dashboard

These are the two screens every session passes through: the gate that establishes who is working (and therefore which of the two roles of D-36 the rest of the application will obey) and the first screen behind it, which answers what needs doing this month. Everything visible below is Thai (D-02); the English names Login and Dashboard survive only as route and identifier, never as UI copy.

Design decisions taken in this document
  • The login identifier is ชื่อผู้ใช้ only, not "Username / Email". PRD §19 lists "Username / Email", but D-46 fixes the Users page field list with no email address and the ADR's users table has username and no email column. One identifier field satisfies the PRD; adding an email field would create a column nothing writes.
  • No "จดจำฉัน" checkbox and no "ลืมรหัสผ่าน" link that does anything. D-37 gives a rolling 8-hour session and states that Admin resetting a password from the Users page is the only recovery path in v1, so the footer is a sentence, not a link.
  • The Dashboard mockup shows the period กันยายน 2026 in its end state — all 67 bills approved, i.e. immediately after the PRD §28 demo approves room 205 live. That is the only state in which D-44's binding common-area figure 67 × 30 × 35 = 70,350.00 appears on screen, because D-41 excludes Draft bills from every money tile.
  • "Today" in the mockups is 8 ก.ย. 2026, three days past the 5 ก.ย. 2026 due date of PRD §28, so both รอชำระ and เกินกำหนด are visible at once. D-20 freezes each bill's own due date, so the nine bills approved on 5 ก.ย. carry a due date of 8 ก.ย. and are correctly not overdue.
  • Money in a KPI tile is written ฿151,370, in a table 2,016.00. D-03 permits the ฿ glyph in mockups where space is tight; a 22 px value inside a 179 px tile is that case. Tables and Bill Detail keep two decimals. The running application may render the tile as 151,370 with บาท in the label — the figure is what is binding, not the glyph.
  • No D-39 confirmation dialog is reachable from either screen. All six call sites live on Monthly Billing, Bill Detail, Payment, Announcements, Tenants and Rooms. Logout is a plain POST /logout with no dialog, because D-39 fixes the list at six and logging out destroys nothing.
Where the Dashboard figures come from

D-44 is explicit that PRD §16's ยอดค่าน้ำ 18,500 and ยอดค่าไฟ 62,500 are arithmetically impossible at the fixed rates (18,500 is not divisible by 18; 62,500 is not divisible by 8) and may not be used as expected values anywhere. Only 80 / 67 / 13 and 70,350.00 are reproduced from the PRD. The water and electricity totals on this page are therefore constructed so that every figure divides cleanly and the three money tiles reconcile:

น้ำ 1,030 หน่วย × 18.00 = 18,540.00  ·  ไฟ 7,810 หน่วย × 8.00 = 62,480.00  ·  ส่วนกลาง 67 × 30 × 35.00 = 70,350.00
เรียกเก็บ 151,370.00 − รับชำระ 124,180.00 = ค้างชำระ 27,190.00

The same twelve-month series feed the two charts; the last column of each chart is this period. Any test that asserts a Dashboard number must assert against these, never against PRD §16.

H1 Juristic Platform plus the Thai subtitle, verbatim from D-01 — the login page is the one surface that shows the product name, because the apartment name is not yet known (Settings is behind the session). No logo image: the design system ships no asset and one is not needed. Static; not interactive.
  2. ชื่อผู้ใช้. A single identifier field, name="username", 44 px tall with 16 px text so iOS and Android do not zoom on focus. autocapitalize="none" and spellcheck="false" because a username typed on a phone keyboard is otherwise capitalised. Validation: required. Empty on submit renders .field.invalid and the message กรุณากรอกชื่อผู้ใช้ under the input; the typed value is preserved on every failure (D-40). No live validation while typing — the first error appears on submit.
  3. รหัสผ่าน. type="password", autocomplete="current-password". Required; empty on submit gives กรุณากรอกรหัสผ่าน. The value is never echoed back into the field after a failed attempt, on any error path. No show/hide toggle in v1 and no minimum-length hint on this screen — password rules belong to the Users page (D-46), not the gate.
  4. เข้าสู่ระบบ. The single primary action, full width and 44 px (.btn.primary.lg.block), also the submit target of Enter from either field. On submit it becomes .btn.is-loading and disabled, so a double submit is impossible before the response lands. Success is a 302: admin to /dashboard, staff to /readings — staff never lands on a page they are 403'd from. The form posts a CSRF token issued on the GET (D-37).
  5. Recovery footer. A sentence, not a link. D-37 and D-46 make Admin's ตั้งรหัสผ่านใหม่ on the Users page the only recovery path in v1, so a self-service link would lead nowhere. The second line is the apartment name from Settings, rendered server-side; it is the one hint that the reader is at the right building's URL.

ลืมรหัสผ่าน? ติดต่อนิติบุคคลเพื่อตั้งรหัสผ่านใหม่

  1. One banner, above the form. .notice.bad re-rendered by the same POST handler (D-40: never a redirect, never a lost form). The wording never says which half was wrong — an attacker must not learn that a username exists — so there is no per-field message here, and the banner is the only place the failure is stated.
  2. Both fields carry .field.invalid, neither carries a message. Marking only the password would leak exactly what the banner refuses to say. The username keeps its typed value; the password is cleared and takes focus. After the tenth failed attempt from one IP inside 15 minutes the banner is replaced by the rate-limit text and the button becomes .btn.is-disabled (D-37).
  3. The phone layout is the same card. .login-card is max-width:360px, so a 390 px device shows the desktop composition unchanged with 24 px of padding either side — there is no separate mobile login template. Inputs stay 44 px with 16 px text, which is what keeps Chrome for Android from zooming (D-45).

  1. Sidebar, built from the role matrix. The header shows the apartment name from Settings with Juristic Platform in 11 px beneath it (D-01). The eight working pages carry the D-02 Thai labels in workflow order; ผู้ใช้งานระบบ and ตั้งค่า sit under a ระบบ divider because they are configured once, not used daily. The .count pill on บิลประจำเดือน is the outstanding-bill count (15) for the selected period, not a notification badge — it disappears at zero. Staff render a three-item version of this list; the items are never rendered-and-hidden, because D-36 requires the amounts behind them to be absent from staff responses, not merely invisible.
  2. Month picker — the only control on the page. D-41 scopes every tile and the donut to one selected billing period, defaulting to the current calendar month. ‹ and › step one month and reload with ?period=YYYY-MM; the label is the D-03 display form กันยายน 2026 while the query string stays ISO. Stepping past the newest period with data disables ›. The two 12-month charts deliberately do not follow the picker — they always end at the selected period and look eleven months back, which is what makes the current column comparable.
  3. Room tiles — the only figures reproduced verbatim from PRD §16. ห้องทั้งหมด = COUNT(rooms); มีผู้เช่า = COUNT(rooms WHERE status='Occupied'); ห้องว่าง is the difference, never a third stored count. They are period-independent, which is why they are also the only money-free tiles staff can see. Not clickable in v1 — filtering ห้องพัก by status is that page's job.
  4. Utility tiles carry their own arithmetic in the .sub line. Each is SUM(bill_items.amount) by item_type over approved bills of the period, and the sub-line restates it as units × rate so an examiner can divide on the spot. The left rule is the utility accent (water / elec / fee) — the same three colours the LINE bill and the receipt use, so the colour means "ค่าน้ำ" everywhere in the product, never "series 1".
  5. ยอดเรียกเก็บทั้งหมด excludes ฉบับร่าง, and says so. "ไม่รวมฉบับร่าง" is not decoration: D-41 defines approved as the stored status being Unpaid or Paid, so a Draft bill contributes to no money tile. Without the sub-line the first question at the demo is why the total moved when nothing was paid. In this mockup all 67 bills are approved, so the three utility tiles sum exactly to this one: 18,540.00 + 62,480.00 + 70,350.00 = 151,370.00.
  6. ค้างชำระสะสมทุกงวด is the one deliberately all-time tile (D-41). It equals the period tile here only because D-44's seed leaves every earlier period fully paid; the sub-line says so, otherwise the repeated ฿27,190 reads as a copy-paste defect. In a real second month of operation the two diverge, and that divergence is the number the office chases.
  7. 12-month usage charts, inline SVG, one series each. Units, not baht — the money view is the tiles, and a second y-axis is never added to a chart. One series means no legend: the card title names it. Only two bars are labelled, the twelve-month peak (เม.ย. 2026, hot season) and the selected period, so the eye lands on the comparison instead of reading twelve numbers. The other bars sit at 55% opacity, which is emphasis, not a second category. Bars are anchored to the baseline with 4 px rounded tops and a 12 px gap. In the running application the same series arrive from GET /api/dashboard/charts?period=2026-09 and are drawn by Chart.js; hovering a bar shows "เม.ย. 2026 · 1,115 หน่วย".
  8. Bill-status donut. Counts, not amounts — the money is already in three tiles above, and D-41 specifies this chart as a Paid vs Unpaid+Overdue count. The centre carries the total (67 ใบ) so the ring never has to be measured. เกินกำหนด is hatched as well as red: red and amber sit closer together than a colourblind reader can resolve, and the palette itself is fixed by the design system, so texture is the available fix. Every slice is also named and counted in the legend, so identity is never carried by colour alone. Segments are separated by a 4 px gap.
  9. The reconciliation block — the identity D-41 requires to hold on screen. Billed − collected = outstanding, printed as a subtraction rather than left for the reader to do across three tiles. If these three ever disagree, a bill in the period is missing one of its three bill_items, which is a defect with its own assertion. Two decimals here, because this is a money statement and not a headline tile (D-03).
  10. ทางลัด — navigation, not new actions. Four links to pages that already exist, ordered by how often the office opens them: รับชำระเงิน is .btn.primary because taking cash at the counter is the daily job; บิลประจำเดือน is .btn.secondary because it is the monthly one. Nothing here performs an action, so nothing here opens a D-39 dialog — a "generate bills" button on the Dashboard would be a destructive action two clicks from a login.
  11. ห้องที่ค้างชำระ — the one list on the page. Sorted by amount descending, capped at the period's overdue bills; the ghost link opens D-42's full arrears report, which ages every Unpaid bill across all periods into 1-7 / 8-30 / 31-60 / 61+ buckets. Every status cell carries data-status="Overdue" (D-02) so a test asserts the English identifier while the reader sees เกินกำหนด. The LINE column exists because D-44 seeds 13 tenants with no binding and D-30 defines a ไม่มี LINE path — a room that cannot be reminded is a room the office must phone. The row action jumps to รับชำระเงิน with the room pre-filled; it never confirms a payment from this page. The footer states the split between the six overdue bills and the nine that merely came due today, so 15 ใบ in the tile above reconciles with 6 rows in the table.

Handover notes for the engineer
  • Ten tiles, one query. All ten KPI values come from services/reports.js in the page render, not from /api/dashboard/charts; only the three chart series are fetched. That keeps the D-45 target of a list page in ≤ 2 seconds honest even when the chart endpoint is slow.
  • The staff branch is a different query, not a different template. views/pages/dashboard.ejs renders whatever tiles the controller passes; the controller asks services/reports.js for the staff set when req.user.role === 'staff', so no amount is ever serialised into a staff response (D-36).
  • Charts in production are Chart.js, not this SVG. The inline SVG here exists so the mockup needs no library; the shipped page uses the same geometry — one series per chart, units on the y-axis, the current period as the last column, direct labels only on the peak and the current period.
  • The hatched เกินกำหนด segment is a requirement, not decoration. --ui-overdue and --ui-unpaid are 11.6 ΔE apart in normal vision and 5.3 ΔE under protanopia — below the readable floor. The design system's status colours are fixed, so the segment carries a 45° texture and the legend carries the count. Reproduce both in Chart.js with a pattern fill, or the chart is unreadable for roughly one examiner in twelve.
  • Every status element needs data-status. Six table cells and three legend rows on this page. It is what lets the test plan assert on Draft / Unpaid / Paid / Overdue while the screen stays Thai (D-02).
