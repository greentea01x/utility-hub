Design Foundations & User Flows

This section is the design contract for every screen mockup in this document set. It fixes the principles, the people, the map, the flows and the component vocabulary; the screen chapters that follow spend those decisions instead of re-taking them. Everything visible to a user is Thai (D-02); every identifier in this document — page names, statuses, class names, routes — stays English, because that is what the code, the API payloads and the test selectors use.

Two stylesheets, one boundary

The documentation is styled by docs/_shared/template.html. The product UI is styled by parts/design/tokens.css, in which every rule is scoped under .screen and every custom property is prefixed --ui-. A mockup is therefore always written as <div class="device desktop"><div class="screen">…</div></div> (or device phone / device print). The two systems can never collide, and the same file ships as public/css/app.css with the .screen prefix removed.

1. Design principles

Five principles, each traceable to a decision and each falsifiable — if a screen breaks one, the screen is wrong, not the principle.

1 · Mobile-first for staff, desktop-first for the office

Three surfaces are phone-sized and must work at 360 × 640 on Chrome for Android: Login, Meter Reading and the reduced Dashboard. Everything else is an office surface designed at 1280 px and not required to work below 768 px (D-45). One stylesheet serves both; the layout switches on container width, never on a user-agent sniff.

2 · One-hand meter entry

A technician stands at a meter box holding a phone in one hand. Each room is a self-contained card with its own บันทึก button and one request (D-15); nothing is a 67-room form. Inputs are inputmode="numeric", targets are ≥ 44 px, previous readings are read-only text, and a dead spot loses at most the room being typed.

3 · Error prevention on money actions

Four actions move money or send irreversible messages: อนุมัติและส่งบิล, ยืนยันรับเงินสด, ส่งประกาศ, ยกเลิกการชำระเงิน. Each states its exact effect — amount, room, billing period, recipient count — in a dialog before it runs (D-39), and each is guarded server-side as well, because a disabled button is not a guard.

4 · Thai-first copy, English identifiers

Every label, button, badge, error and LINE message is Thai and is written once in the templates — there is no language switcher and no i18n framework (D-02). English survives as data-status="Unpaid", route names and column names. Money is 1,790.00 in tables and 1,790 บาท in sentences and LINE; dates are Gregorian (D-03).

5 · Glanceable status

The office question is always "which rooms still owe money?". Status is a badge carrying a Thai word, a colour and a data-status hook — never colour alone (§9). Overdue is derived at render time from Unpaid plus a past due date and is never stored (D-21), so no screen may offer an action that "marks a bill overdue".

2. Personas

คุณนิด — Admin / นิติบุคคล

Device
Office desktop, Chrome, 1280–1920 px, mouse and keyboard
Frequency
Daily at the counter; a heavy hour once a month at approval
Owns
Rates, bills, approval, cash, receipts, tenants, announcements, users, settings

Goals — every occupied room billed with nothing missed; the cash drawer reconciles against the system at closing; know today which rooms are in arrears and for how long; answer "why is my bill 1,790?" with the meter numbers on screen.

Frustrations — an Excel file that two people edited; re-typing the same LINE message 67 times; a tenant disputing a reading with no history to show; discovering at month end that three rooms were never read.

ช่างสมชาย — Staff / เจ้าหน้าที่ช่าง

Device
Personal Android phone, 360 × 640, one hand, patchy signal in stairwells
Frequency
One reading round per month, 67 rooms, target ≤ 15 minutes (D-45)
Owns
Meter readings and meter replacements only — never an amount, a rate or a payment (D-36)

Goals — walk each floor once, in room order; never re-walk a floor because a save was lost; know at a glance which rooms are still outstanding; hand the round to the office with one button.

Frustrations — a form that loses everything when the lift kills the connection; tiny targets while wearing gloves; not remembering whether room 312 was already entered; a keyboard that is not numeric.

คุณแอน — Tenant / ผู้เช่า

Device
LINE on her phone. No login, no app, no web account — ever (D-05)
Frequency
Three or four messages a month
Owns
Nothing in the system; she is a recipient and a person at the counter

Goals — know the amount and the due date without asking; understand how the amount was reached; get proof that her cash was recorded.

Frustrations — a paper slip pushed under the door and lost; a total with no breakdown; no confirmation after paying; being chased for a bill she already settled.

The tenant is not a user of the web application

Every tenant-facing surface in this design set is a LINE message or a printed A5 sheet. No screen, route, empty state or error page is ever designed for a tenant, and no mockup may show a tenant login (PRD §4, D-05).

4. Navigation model per role

One shell, two navigations, chosen by role at render time — not two applications. Staff never see a link they cannot open, and the 403 page exists for the case where a staff user types an Admin URL directly (D-40).

The tab order is deliberate: the reading round is the staff job, so it is the landing page and the first tab. The staff Dashboard shows room counts and this period's reading progress only — no money reaches a staff response body at all (D-36).

6.1 Validation timing

The one blocking rule at the meter

When เปลี่ยนมิเตอร์ในรอบนี้ is off and the current reading is below the previous one, บันทึก is disabled and the field shows เลขมิเตอร์ปัจจุบันน้อยกว่าเดือนก่อน (1,250) กรุณาตรวจสอบ. Ticking the checkbox reveals เลขสุดท้ายของมิเตอร์เดิม, เลขเริ่มต้นของมิเตอร์ใหม่ and a required reason, and replaces the rule instead of bypassing it (D-13). The two soft flags — ใช้สูงผิดปกติ and ไม่มีการใช้งาน — never block a save.

6.3 Errors and loading

  • Failed save — a .notice.bad above the form with ลองอีกครั้ง; every typed value is preserved. On the phone reading screen the notice lives inside the room card and never reloads the page (D-40).
  • Unauthorized — a full Thai 403 page: ไม่มีสิทธิ์เข้าถึงหน้านี้ · บัญชีของคุณเป็นเจ้าหน้าที่ กรุณาติดต่อนิติบุคคล with a button back to จดมิเตอร์. Never a silent redirect, so the permission matrix is testable row by row.
  • Lists — three to five .skeleton.row placeholders, never a centred spinner over an empty page.
  • Actions — the pressed button takes .is-loading and disabled; nothing else on the page is blocked.
  • Long jobs — the approve result screen shows a .progress bar driven by the drain loop with a running count, because a 67-room send takes up to three minutes (D-19, D-45).
  • Success — a .toast.ok for reversible, low-stakes saves; a full result screen for anything that sent a LINE message or moved money.

6.5 Undo — where it exists and where it deliberately does not

No toast-with-undo anywhere in this product

An undo window would force every outbound LINE message into a delay queue, and a message already delivered cannot be recalled by any API LINE offers (D-39, D-35). Instead, the two reversible money paths are explicit, audited, Admin-only actions with a required Thai reason: ตีกลับเป็นฉบับร่าง on an Unpaid or Overdue bill — available only on a room's most recent bill (D-22) — and ยกเลิกการชำระเงิน, which returns cash first, keeps the receipt number and stamps the receipt ยกเลิก (D-25). Everything else is safe because it is reversible by ordinary editing (a Draft bill recalculates on every reading save) or because it never happened yet (a dialog stands between the click and the effect).

9. Accessibility

  • Contrast — every badge pairs its text token with its own -soft background at ≥ 4.5:1, and white on --ui-brand is 7.8:1. The four palette values that failed this check were darkened rather than accepted: water, electricity, danger and overdue. Muted text (--ui-muted on white, 4.7:1) is the lightest text permitted, and it is never used below 12 px.
  • Status is never colour alone — a status is always a Thai word inside a badge, plus data-status for tests. A colour-blind cashier reads ชำระแล้ว, not "the green one"; a printed page in greyscale still says it.
  • Targets — 44 × 44 px minimum on every phone surface (--ui-tap): the meter inputs, บันทึก, the filter chips and the bottom tabs. Desktop rows may use the 38 px default, but never for a destructive action.
  • Labels — every input has a real <label>; a placeholder is never the label, because it disappears exactly when a Thai speaker re-checks what they typed. Hints and errors are wired with aria-describedby, and .field.invalid also sets aria-invalid="true".
  • Focus — a visible 2 px --ui-focus ring on every interactive element, never outline:none. Focus order follows the DOM: topbar → filters → list → primary action. Opening a dialog moves focus to its title and traps it; Esc always cancels and never confirms; closing returns focus to the button that opened it.
  • Numbers — inputmode="numeric" on every meter and money field, and font-variant-numeric: tabular-nums on every money column so columns of baht line up.
  • Language and structure — <html lang="th">, one <h1> per page, tables with real <th scope>, and a skip link to .main as the first focusable element.
  • Motion — the only animation is a loading spinner; there is nothing to disable, and no auto-advancing carousel, toast queue or scroll-jacking exists.

Container queries, not viewport queries

The switch is written as @container app (max-width:767px) against .app, not as a media query. In the running app the result is identical, because .app fills the viewport. In this document set it is what makes a phone mockup inside a .device.phone frame render the phone layout while a desktop mockup on the same page renders the sidebar — one stylesheet, no duplicated mobile variants, and no chance of a mockup drifting from the product.

11. Assumptions recorded by design

  1. Page routes. The ADR fixes the naming rule (lowercase, plural, hyphenated) and quotes /bills, /bills/:id, /readings and /announcements. The remaining routes in §3 — /login, /dashboard, /rooms/:id, /tenants, /payments, /receipts/:id, /bills/:id/invoice, /reports, /settings, /users — are derived from that rule and from the routes/ and views/pages/ file lists. If engineering names one differently, this table follows the code.
  2. Brand colour. The PRD names no brand colour. Navy #1b4fa0 was chosen because it is unmistakable against all three utility accents (cyan, amber, violet) and against the paid/overdue pair, and because white text on it clears 7:1. No logo, gradient or illustration is introduced — nothing in the document set implies an asset the team has not made.
  3. Single light theme. The doc template paints every mockup screen white and the product targets one office desktop and one staff phone, so no dark palette is defined. Adding one later is a token block, not a redesign.
  4. Icons are emoji. 💧 ⚡ 🏢 📝 🧾 and the nav glyphs are Unicode emoji rendered by the platform font — zero assets, zero licensing, and they already appear in the LINE templates fixed by D-31. Any icon carrying meaning is paired with a Thai word.
  5. Illustrative Dashboard figures. Water and electricity totals in §8.1 are invented for the mockup. Per D-44, only the room counts (80 / 67 / 13) and the common area total (70,350.00) from PRD §16 are reproducible; PRD §16's 18,500 and 62,500 are not and are never used as expected values.
  6. Demo names. ศุภาลัย เรสซิเดนซ์, the address, the tax ID and every tenant name are fictional seed values (D-44). No real tenant data appears in any mockup.
  7. Reserved LINE components. .flex-card and .rich-menu are specified because the brief asks for them, and are marked reserved in both the stylesheet and §8.6 because D-31 fixes v1 to plain text. A v1 screen using them is a defect.
