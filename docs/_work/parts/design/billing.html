Monthly Billing & Bill Detail

These two screens are the money spine of the product: Monthly Billing is where an Admin sees a whole period at once and pushes a batch of Draft bills through the single approval gate (D-19), and Bill Detail is where one bill is checked line by line, approved, delivered over LINE, paid, and — when something is wrong — corrected. Both are Admin-only surfaces; Staff never reach them and never receive an amount in an API response (D-36). Every figure below is the PRD §28 demo room reproduced exactly: room 205, 30 ตร.ม., water 1,250→1,260 = 10 units × 18 = 180, electricity 5,280→5,350 = 70 units × 8 = 560, common area 30 × 35 = 1,050, total 1,790 THB, due 5 ก.ย. 2026, paid 3 ก.ย. 2026, receipt REC-202609-000852.

Design decisions taken in these two screens (recorded, not asked)
  • The list mockup is dated 8 ก.ย. 2026, the detail mockups 1–3 ก.ย. 2026. One period page cannot show all four statuses on the day of approval, because Overdue is derived from due_date < CURDATE() (D-21). The list is therefore shown a week into the period, when the first batch (approved 1 ก.ย., due 5 ก.ย.) has aged into เกินกำหนด, a second small batch (approved 7 ก.ย., due 10 ก.ย.) is still รอชำระ, three late-read rooms are fresh ฉบับร่าง, and room 205 — approved 1 ก.ย., paid 3 ก.ย. — is ชำระแล้ว. All four badges are real states of the same period, not a display sampler.
  • Generation has no confirmation dialog. The brief asked for one, but D-39 fixes the confirmation list at exactly six call sites and generation is not among them. Generation is idempotent, never touches an approved bill and only ever writes or rewrites Drafts (D-18), so it runs on click and reports the D-18 summary as an inline .notice. Adding a seventh dialog would contradict a binding decision; the destructive act in this period is approval, and that one is guarded.
  • Checkboxes exist only on Draft rows. D-19 enables the bulk button when at least one selected bill is Draft; rather than letting an Admin select 43 paid bills and silently skip them, non-Draft rows render a disabled checkbox with a Thai title. The selected count and the button count are therefore always the number of bills that will actually change.
  • The revert-to-Draft dialog is specified in the copy table, not drawn. It is the shared D-39 dialog with a required reason field, identical in shape to the void-payment dialog; a fourth Bill Detail frame would add no information the copy table does not carry.
  • Every mockup is Admin. The Staff view of both routes is the Thai 403 page (D-40), specified in each states table rather than drawn twice.

  1. 1Month picker (.month-picker) — the period is the whole page's query, ?period=2026-09, rendered "กันยายน 2026" and defaulting to the current calendar month in Asia/Bangkok (D-11). The arrows step one month and reload the page server-side; there is no period lock and no "closed" state, so any month can be opened at any time. Choosing a month with no bills lands on the empty state.
  2. 2สร้าง/อัปเดตบิลฉบับร่าง — runs generation for the selected period (POST /api/bills/generate, D-18). It creates a Draft for every billable room that has both readings and no bill, recalculates existing Drafts in place, and never touches an approved bill. It runs on click with no dialog (see the decision callout) and answers with annotation 4's summary notice. While it runs the button takes .is-loading and is disabled; a second click can therefore not start a second run, and the unique key (room_id, period) makes a race harmless anyway.
  3. 3อนุมัติและส่งบิล (3 ห้อง) — the page's one primary action and the only irreversible one. Its count mirrors the checked Draft rows live; with nothing selected it renders [disabled] with the hint "เลือกบิลฉบับร่างอย่างน้อย 1 ใบ". Clicking opens the D-39 bulk dialog (frame 1b). Admin only — the button is not merely hidden from Staff, the whole route is (D-36).
  4. 4Generation result notice (.notice.ok) — the verbatim D-18 summary "สร้างบิลใหม่ {a} ใบ · อัปเดต {b} ใบ · ข้าม (อนุมัติแล้ว) {c} ใบ · ยังไม่ได้จด {d} ห้อง". It is a flash rendered after the POST-Redirect-GET, so it survives the reload and disappears on the next navigation. A run that changes nothing still reports honestly ("สร้างบิลใหม่ 0 ใบ"), which is the visible proof that re-running is safe.
  5. 5Unread-rooms banner (.notice.warn, D-23) — persistent, not dismissible, and present for as long as any billable room in this period lacks a bill. Each room code is a link to Meter Reading for that room and period. It never blocks approval: the office approves the bills that exist and re-runs generation when the missing rooms are read. It disappears exactly when the count reaches 0, which is the tester's assertion for "ทุกห้องที่มีผู้เช่าได้รับบิล".
  6. 6Completeness line (D-11) — derived, never stored: "บิลครบทุกห้อง 64/67 · อนุมัติแล้ว 61 · ชำระแล้ว 43", where 67 is the count of billable rooms (Occupied with exactly one Active tenant, D-07) on the generation date. It replaces the period open/close state machine the system deliberately does not have.
  7. 7KPI tiles (.kpi-grid, D-41) — the three money tiles aggregate over the stored status column, status IN ('Unpaid','Paid'), so a Draft is not yet "billed" and an aged Unpaid bill is still counted in ยอดเรียกเก็บ; that is a deliberate aggregation, not a violation of the display rule in D-21. The fourth tile shows the Draft total separately, and is labelled so nobody adds it to the first tile by eye.
  8. 8Status filter chips (.chip-row) — client-side filters over the loaded page plus a server query string; counts are for the whole period, not the visible page. Every count is computed through the shared display-status helper (D-21), so a bill whose due date passed at midnight moves from รอชำระ to เกินกำหนด with no job and no drift. ทั้งหมด is the default and is the only chip that can be active together with a search term.
  9. 9Search (.search) — filters by room code or tenant name inside the selected period; it never crosses periods. Typing narrows the table on keyup with a 200 ms debounce; the selection is preserved while filtering, and the primary button's count keeps counting hidden-but-selected rows, so a filter can never silently shrink a batch.
  10. 10Select-all-in-view — selects only the selectable (Draft) rows of the current page, never all 64 bills of the period, so the count on the primary button is always exactly what will change. With some but not all Draft rows checked it renders indeterminate. Paging away clears the selection; the batch is one page, which is also what keeps the approve transaction small (D-19).
  11. 11Status column — one .badge per bill carrying data-status="Draft|Unpaid|Paid|Overdue" (D-02) so tests assert the English identifier while the human reads Thai. Only three of the four exist in the database; เกินกำหนด is derived at render time from status='Unpaid' AND due_date < CURDATE() (D-21). Nothing on this page can edit a status directly.
  12. 12LINE delivery column (D-30) — per-bill delivery state, independent of money state: ส่งแล้ว, ยังไม่ได้ส่ง — ไม่มี LINE, ส่งไม่สำเร็จ, and "—" for a Draft that has not been sent at all. A LINE outage can never change what this column's row is worth in baht: approval commits first, delivery happens after and outside the transaction.
  13. 13Failed delivery — title carries the reason, the timestamp and attempt_count ("LINE API 500 · 1 ก.ย. 2026 14:32 น. · ลองแล้ว 3 ครั้ง"). Automatic retries stop at three attempts; the Admin's manual ส่งแจ้งเตือนอีกครั้ง on Bill Detail is never capped. The word "blocked" appears nowhere: LINE reports a blocked recipient as a success, and that gap is a listed limitation (D-05 #9).
  14. 14Room 205, the demo row — the room code and ดูบิล both open /bills/1842. The whole row is a link target; tr.is-selected here marks the row the Admin arrived from, not a checkbox selection. Common area is 1,050.00 on every row because all 80 seeded rooms are 30.00 ตร.ม. (D-44).
  15. 15A Draft whose tenant has no LINE binding — flagged before approval, not after, so the office knows it will be handing this room a paper ใบแจ้งค่าใช้จ่าย. Approving it still works; the notification row is written with status='skipped_no_line' and appears in the result summary's ยังไม่ได้ส่ง count (frame 1c). 13 of the 67 seeded tenants deliberately have no binding (D-44).
  16. 16Pagination and selection count — 12 rows per page over up to 67 bills; the page info repeats the live selection count so the primary button's number is verifiable without scrolling back up. Sorting is by room code ascending and is not user-configurable in v1.

  1. 17The shared confirmation dialog (.modal + .dialog) — one component, six call sites, never the browser's native confirm() (D-39). The title carries the count, the body opens with the verbatim D-39 sentence "อนุมัติและส่งบิล {N} ห้อง ผ่าน LINE — ยกเลิกไม่ได้", and the primary button repeats the verb instead of saying ตกลง. The due date is the D-20 rule made visible: MAX(day-of-month 5, approval 8 ก.ย. + 3 days) = 11 ก.ย. 2026, so a late approval can never produce an unpayable window, and every bill in one batch shares one due date. The ไม่มี LINE line is the office's cue to print an ใบแจ้งค่าใช้จ่าย for room 211.

Delivery is a second round trip, so a LINE outage cannot roll back an approval. The button takes .is-loading on click and the dialog cannot be submitted twice; a duplicate request finds no Draft rows left and approves nothing.

  4. 39Payment history — one live payment per bill (D-24, D-26), full amount only, always cash. A voided payment is never deleted: it stays in this table with ยกเลิกแล้ว, its reason and its original receipt number, and a fresh payment adds a second row with a new number. That is what voiding rather than deleting buys — the sequence is unique and monotonic, but explicitly not gapless (D-05 #10, D-27).
  5. 40Audit timeline (.timeline, D-38) — literally SELECT * FROM audit_log WHERE bill_id = ? ORDER BY created_at, with reading edits made while the bill was Draft carrying the same bill_id. Admin-only, read-only, no cross-entity join, no global audit browser in v1. The two .is-key dots are the money events: approval and payment. Reverts appear here with their Thai reason.
  6. 41ส่งแจ้งเตือนอีกครั้ง — the Admin's uncapped manual resend (D-33), the tool of last resort on the day an automatic send failed. Disabled here because the bill is paid and there is nothing to chase; on an Unpaid or Overdue bill it is enabled and pushes the current PRE_DUE or OVERDUE template. Automatic reminders are shown as หยุดแล้ว: PRE_DUE at due − 2, OVERDUE at due + 1, + 8, + 15, nothing after day 15, nothing to a Paid bill, and nothing at all for a bill whose most recent payment was voided (D-25, D-33).
  7. 42The correction path (D-22) — a Paid bill is corrected across the counter, not in the database: the cash goes back to the tenant first, then ยกเลิกการชำระเงิน (Admin, required Thai reason of at least 10 characters, dialog D-39 #5 "คืนเงินสด 1,790.00 บาท ให้ผู้เช่าก่อนยืนยันการยกเลิก") voids the payment and the receipt — both kept, the receipt stamped ยกเลิก — and returns the bill to Unpaid. ตีกลับเป็นฉบับร่าง is therefore disabled until then, with the reason in its title. On an Unpaid or Overdue bill it is enabled instead, and is refused server-side when a later bill exists for the same room: "มีบิลรอบถัดไปแล้ว ไม่สามารถแก้ไขย้อนหลังได้ — กรุณาแก้ในรอบล่าสุด" (verbatim D-22), because the next bill's previous reading is a snapshot of the value being edited. After the fix the bill is re-approved and the tenant receives BILL_CORRECTED (D-31). The system never holds a refund, a credit or a balance (D-05 #4).

Assumptions recorded by these two screens
  • Fictional tenant names, phone numbers and LINE display names throughout; the demo seed carries the same shape (D-44). Room 205's tenant is นายสมชาย ใจดี in every document of this set.
  • Bill id 1842 and batch id 418 are illustrative identifiers, not seeded values. The only seeded identifiers that must reproduce are room 205, the arithmetic 10/70/180/560/1,050/1,790 and the receipt number REC-202609-000852 (D-44).
  • All rooms are 30.00 ตร.ม., so ค่าส่วนกลาง is 1,050.00 on every row of the list; that is the seed, not a rendering shortcut, and it is why PRD §19's 35 ตร.ม. example row is not reproduced anywhere (D-44).
  • Office hours "08:30–17:00 น." and the apartment name come from Settings and are placeholders in the message template, never literals in code (D-31).
  • Twelve rows per page and a 200 ms search debounce are design choices, not decisions from the log; they may change without contradicting anything binding.
  • The Monthly Billing surface targets desktop Chrome and Edge at 1280 px and above and is not required to be usable below 768 px (D-45); the container query in the design system still degrades it to a single column with the bottom tab bar rather than breaking it.
