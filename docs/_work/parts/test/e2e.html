Test Strategy

This section is the QA contract for Juristic Platform. It says what is tested, at which tier, with which tool, against which data, and what has to be true before a build is shown to anyone. Everything below is derived from ADR-001 (binding for stack and conventions), the PM decision log D-01…D-47 (binding for policy) and the engineering specification's FR-01…FR-48. Where this document adds a name, a hook or a file, it is listed in Assumptions recorded by this section and nowhere else.

Three sentences fix the shape of everything that follows. Money is computed in SQL on DECIMAL and never in JavaScript (D-16, ADR A-4), so an amount can only be asserted against a database or a rendered page — never against a JavaScript expression. Overdue is derived from CURDATE() and is never stored (D-21), so a due-date test moves the data, not the clock. Every seed date is computed from the run date (D-44), so a test asserts the arithmetic — 10, 70, 180.00, 560.00, 1,050.00, 1,790.00 — and never the calendar.

1.1 Objectives

O-1 · The number on the receipt is right

Every amount a tenant sees on LINE, on the printed ใบเสร็จรับเงิน or on Bill Detail equals the sum of its own printed lines, and every line equals ROUND(quantity × unit_price, 2) against the rate snapshotted on the bill. A total that disagrees with its lines is the defect this project exists to prevent (D-16, D-41).

O-2 · A double-click cannot lose money

Two cashiers, a double-submitted form and a retrying scheduler all converge on one payment, one receipt number and one LINE message. The guarantees live in eleven unique keys and three generated columns (ADR §6.8 layer 4), so the tests that matter drive HTTP concurrently and assert what the database allowed, not what the button did.

O-3 · Staff never receive an amount

D-36 is stronger than navigation: money is absent from the queries that serve staff, not hidden in a template. Every Staff-forbidden route is asserted twice — HTTP 403 with the Thai page or FORBIDDEN_ROLE, and no digit-grouped amount anywhere in the response body.

O-4 · The graded demo path always runs

The PRD §28 walk — read → generate → approve → LINE → cash → receipt → LINE → Dashboard — is exercised end to end on every push at two tiers: headless in npm run rehearse and through a real browser in E2E-01. A red E2E-01 blocks the merge.

O-5 · Nothing from PRD §24 reappears

No test, fixture, seed row or page object mentions rent, a lease, a gateway, a card, online banking, a slip, a QR code, an IoT meter or AI. A test that would need one of them is a scope defect, not a missing feature (D-05).

O-6 · Failures are legible in Thai

Every rejection path a user can reach is asserted on both halves: the stable UPPER_SNAKE error code that tests read, and the Thai sentence the office reads (ADR §6.3, D-40). Asserting only the status code passes while the screen shows English.

Out of scope for QA, deliberately

  • Load and concurrency benchmarking. D-45 makes no uptime, concurrency or load commitment. The five committed numbers are stopwatch measurements against the seed, taken by hand, recorded in the test log.
  • A browser matrix. D-45 names current Chrome and Edge at ≥ 1280 px for Admin and Chrome for Android at 360 × 640 for Staff. Playwright runs Chromium only; Edge and a real Android handset are checked by hand once per milestone.
  • Print output. Browser print CSS is the one thing in this stack that cannot be automated (ADR A-13.5). The A5 ใบเสร็จรับเงิน is printed on the real office printer by week 9 — a dated manual test, not an assertion.
  • The real LINE platform. Automated tiers never call it. One real link and one real push are performed by hand per milestone against the deployed instance, because the free plan's 500-message allowance is the project's scarcest resource (D-34, R-02).

ADR-001 A-9 amendment — Playwright is added as tier 4, dev-only

ADR §1 lists Playwright under explicitly rejected dependencies, and A-9's reason is sound: "a browser download and a week of setup in a semester that needs the twelfth screen". QA's position is narrower than what A-9 rejected, and this is the amendment being requested:

  • What is added: one devDependency, one playwright.config.ts, one test/e2e/ folder and one CI job. Nothing reaches the runtime, package.json's ten runtime dependencies are untouched, and the deployed process is byte-identical.
  • TypeScript does not reintroduce a build step. A-1 removes the build step for the application; Playwright compiles its own specs, so test/e2e/*.spec.ts needs a nine-line tsconfig.json scoped to that folder and no toolchain the app can see. npm start, npm run dev and the Render build command are unchanged.
  • Why it earns its place: four of the seven scenarios assert something no headless tier can reach — a D-39 dialog that must state the exact effect before an irreversible action, the reading round on a 360 px viewport (D-45 target 1), the Thai 403 page (D-40), and the derived เกินกำหนด badge. The rehearsal script proves the path runs; only a browser proves the screens agree with the database.
  • Cost containment: Chromium only, workers: 1, retries: 0, seven specs. Setup is npx playwright install --with-deps chromium in one CI job — measured at roughly two hours of work, not a week, because the seed already rebuilds the whole demo in one command (D-44).
  • Cut order: if the semester runs short, tier 4 is cut before item (1) of A-14, because it ships no screen. Tier 3 is the safety net that survives the cut, and it is the tier A-14 already protects.

If the architecture judge declines this amendment, every scenario below stays valid as a written manual test and the Playwright code in §2 is deleted; nothing else in this document changes.

What is deliberately not a tier

  • No coverage gate. ADR §6.9 is explicit and QA agrees: the enforced artefact is the list of tests, not a percentage. A missing test from the tier-2 list is a gap; a coverage number is a number. The traceability matrix in §1.9 replaces it.
  • No snapshot testing. Every Thai string in this product is a decision-log value. A snapshot would make an accidental copy change pass review as "just update the snapshot"; asserting the verbatim D-02/D-31/D-39 string makes the change visible in the diff.
  • No component tests. There are no components — the views are EJS rendered by the same process that owns the data, so tier 2 already renders them.

1.4.1 The demo fixture — test/fixtures/reset-205.sql

E2E-01 starts one step earlier than the seed does: the seed hands the demo a room 205 that is already read and already has a Draft bill, because the live demo only approves it. A test that must prove the reading step needs room 205 unread. This fixture re-arms it, in one file used by both tier 2 and tier 4, and it is the only fixture that touches the demo room.

-- test/fixtures/reset-205.sql
-- Re-arms the PRD §28 demo on room 205: no reading, no bill, counter at 851.
-- Every date is derived from CURDATE(); nothing here hard-codes a calendar (D-44).
-- Applied ONLY to juristic_test / juristic_e2e. Never to a demo database.

SET @room   := (SELECT id FROM rooms WHERE room_code = '205');
SET @period := DATE_FORMAT(CURDATE(), '%Y-%m');
SET @prev   := DATE_FORMAT(CURDATE() - INTERVAL 1 MONTH, '%Y-%m');
SET @bill   := (SELECT id FROM bills WHERE room_id = @room AND period = @period);

-- Unwind the current period for this room, child rows first.
DELETE FROM notifications WHERE bill_id = @bill;
DELETE FROM receipts      WHERE payment_id IN (SELECT id FROM payments WHERE bill_id = @bill);
DELETE FROM payments      WHERE bill_id = @bill;
DELETE FROM bill_items    WHERE bill_id = @bill;
DELETE FROM audit_log     WHERE bill_id = @bill;
DELETE FROM bills         WHERE id      = @bill;
DELETE FROM meter_readings WHERE room_id = @room AND period = @period;

-- Pin last month's closing readings so the §28 arithmetic reproduces whatever
-- the seed's history generator produced. previous_reading is INT UNSIGNED, so the
-- subtraction is CAST to SIGNED and floored at 0 to satisfy CHECK (units >= 0).
UPDATE meter_readings
   SET current_reading = 1250,
       units = GREATEST(CAST(1250 AS SIGNED) - CAST(previous_reading AS SIGNED), 0)
 WHERE room_id = @room AND period = @prev AND utility_type = 'water';

UPDATE meter_readings
   SET current_reading = 5280,
       units = GREATEST(CAST(5280 AS SIGNED) - CAST(previous_reading AS SIGNED), 0)
 WHERE room_id = @room AND period = @prev AND utility_type = 'electric';

-- The counter is not gapless (D-26, D-27); it is reset so the next allocation is 852.
UPDATE counters SET seq = 851 WHERE name = 'receipt';
Two deliberate properties of this fixture
  1. It mutates last month's closing reading and leaves last month's bill alone. That is correct, not sloppy: bill_items are snapshots taken at generation (D-09, D-17), so a Paid historical bill does not and must not recompute. The fixture is asserting the same invariant the product relies on.
  2. It resets the receipt counter to 851, not to 0. The 852 in REC-<YYYYMM>-000852 comes from the seed offset, and the sequence is unique and monotonic but explicitly not gapless (D-26, D-27). No test may assert gaplessness; the two assertions permitted are that no two receipts share a number and that a later payment never receives a lower one.

There is no HTTP mock server and no cassette library — that is an ADR-level choice, and this plan keeps it.

1.5.1 The four-line change to test/helpers/fakeLine.js

// test/helpers/fakeLine.js — spec §5.8.2, plus the outbox file the browser tier reads.
import { appendFileSync } from 'node:fs';

export const fakeClient = () => {
  const outbox = [];
  const record = (e) => {
    outbox.push(e);
    if (process.env.LINE_OUTBOX_FILE) appendFileSync(process.env.LINE_OUTBOX_FILE, JSON.stringify(e) + '\n');
    return { status: 200 };
  };
  return {
    outbox,
    pushMessage:  async (to, msg, key) => record({ api: 'push',      to, msg, key }),
    multicast:    async (to, msg, key) => record({ api: 'multicast', to, msg, key }),
    replyMessage: async (token, msg)  => record({ api: 'reply',      token, msg }),
  };
};

A JSONL file rather than an HTTP mock server, for three reasons: it costs four lines instead of a second process and a port; it cannot drift from the client the integration tier already uses, because it is that client; and it never changes what the server does, so a passing E2E is evidence about the shipped code path and not about a test double. The rejected alternative — a fake LINE server on 127.0.0.1 with LINE_API_BASE pointed at it — would additionally exercise the SDK's own HTTP layer, which is not code this team wrote and not code that can break the demo.

Test mode changes who receives, not what is recorded

line_test_mode defaults ON in every environment (D-34) and redirects every outbound message to one whitelisted userId while still recording the intended recipient on the row. So in every automated tier the outbox entry's to is the test account and the notifications.recipient_user_id is the tenant. A test that asserts the recipient must read the database row; a test that asserts the message text may read the outbox. Getting this backwards produces a test that passes with test mode off and fails with it on — the exact opposite of what is wanted.

/** POSTs one signed event. Pass tamper: true to assert the 401 path. */
export async function postEvent(baseUrl, event, { tamper = false } = {}) {
  const body = JSON.stringify({ destination: DESTINATION, events: [event] });
  return fetch(baseUrl + '/line/webhook', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',

The shell equivalent is spec §5.8.3 and stays in the runbook for hand-testing against the deployed instance. Two properties matter and are asserted: the endpoint answers 200 before doing any work (D-29, D-43 — LINE disables an endpoint that repeatedly fails to answer, and a disabled webhook silently kills the only route by which a userId ever reaches the system), and a tampered signature is 401 with nothing written. A fabricated replyToken is harmless under LINE_MOCK=1; against the real dev channel it would fail with 400 while the binding — the part under test — still happens.

1.6 Clock control for due and overdue tests

The clock cannot be frozen, and trying is the wrong answer

Overdue is produced by CASE WHEN b.status = 'Unpaid' AND b.due_date < CURDATE() THEN 'Overdue' ELSE b.status END — evaluated by MySQL, on the database server, at query time (D-21). A JavaScript fake timer cannot move CURDATE(). Worse, it would desynchronise todayBangkok() from CURDATE() and put the system into a state it can never actually reach, so the test would be asserting fiction.

The technique is to move the data, not the clock. One UPDATE per bill, expressed relative to CURDATE(), and both the SQL expression and the JS helper agree because both still read a real, consistent today.

-- Any bill can be aged or brought forward with one statement.
UPDATE bills SET due_date = CURDATE() + INTERVAL 2 DAY WHERE id = ?;  -- PRE_DUE fires today
UPDATE bills SET due_date = CURDATE() - INTERVAL 1 DAY WHERE id = ?;  -- displays Overdue; days_overdue = 1
UPDATE bills SET due_date = CURDATE() - INTERVAL 8 DAY WHERE id = ?;  -- days_overdue = 8

1.6.1 Two consequences that catch people out

  1. The reminder ladder needs six bills, not six clock jumps. notifications.dedupe_key includes send_date, and send_date is today (D-30, ENG-3). Aging one bill to −1, running the job, then aging the same bill to −8 and running again produces the same dedupe key and UPSERTs the same row — no second message, correctly. So D-33's ladder is proved with one job run against six differently-aged bills, which is also how the production system actually behaves on any given morning.
  2. The daily job will not run twice in one day, by design. uq_job_runs(job_name, run_date) makes a second daily call a no-op returning already_ran: true (D-32). A test that needs a second run either deletes the row — DELETE FROM job_runs WHERE job_name = 'daily' AND run_date = CURDATE(); — or uses the Settings path, which runs the identical code as daily_manual and deliberately skips the guard. Both are asserted: the no-op is the requirement (FR-37).
Defect candidate raised by writing the due-date oracle · S3 · documentation

D-20 and ADR §4 both state due_date = MAX(day-of-month of the period month, approval_date + 3 days), "clamped to the month's last day". Read literally, an approval on 30 September for period 2026-09 gives MAX(5 Sep, 3 Oct) = 3 Oct, which the clamp would then pull back to 30 September — a due date before the three-day floor D-20 exists to guarantee, and one day after approval. The reading that preserves the intent is that the clamp applies to the day-of-month term only (it exists for a due_day that a short month lacks, which the 1–28 range already prevents), and never to the result of the MAX. QA implements the oracle that way, asserts it in test/unit/dueDate.test.js, and asks for one clarifying clause in D-20 and ADR §4. Until that clause exists, a late approval near month end is the one place the product and this test plan could legitimately disagree.

1.7 Entry and exit criteria

Entry criteria — a build QA will accept for testing

  • npm run lint is green and npm ci installs from the committed lock file.
  • npm run db:reset completes and prints 80 rooms · 67 tenants · 54 LINE-linked · rates 18.00/8.00/35.00 · due day 5. A seed that prints anything else is rejected before a single test is run.
  • npm run test:unit is green — a red unit tier means the arithmetic is wrong and no higher tier's result is meaningful.
  • GET /healthz returns {"data":{"ok":true,"db":"up"}} on the target instance.
  • settings.line_test_mode = 1, verified by reading the Settings page, not by trusting the default.
  • The pull request names the decision ids it implements and says "requires db:reset" on the first line when the schema or seed changed.

Exit criteria — per milestone

  • Every FR in the milestone's scope has at least one test that names its id, and the traceability grep of §1.9 reports zero uncovered FRs for that milestone.
  • Zero open S1. Zero open S2 on the demo path (Login → จดมิเตอร์ → generate → อนุมัติและส่งบิล → LINE BILL → ยืนยันรับเงินสด → receipt → LINE PAID → Dashboard).
  • All four tiers green in CI on the merge commit, not only on a developer's laptop.
  • npm run rehearse green against the milestone's own database, with its six §28 numbers pasted into the milestone note.
  • The five D-45 numbers measured with a stopwatch against the full seed and recorded, even when one of them misses: an unmet target is a known figure, not a silent one.
  • Every new Thai string checked verbatim against its decision-log entry. A reworded confirmation dialog is a D-39 defect, not a copy edit.

Exit criteria — the defence build, additionally

  • The A5 ใบเสร็จรับเงิน printed on the office printer within the last seven days, one page, Thai unbroken, margins intact (R-06).
  • The webhook re-verified green in the LINE console after the final deploy (D-43 — the one runbook line that has silently killed the linking flow).
  • The local fallback rehearsed for real: local app, local MySQL restored from the newest dump, webhook disabled, test mode ON (R-10).
  • A mysqldump committed the day before, and the demo account's password known to two people.

Four escalation rules that override the table
  1. Any defect that changes a number a tenant sees is S1, however small the delta and however unlikely the path. 1,790.00 versus 1,789.99 is not a rounding preference.
  2. A missing or wrong audit_log row on a money or bill-state change is S1 even when the amount is correct. D-38 makes the trail part of the transaction; an untraceable correct number is an untestable system.
  3. Any role leak is S1. A Staff response containing a rate, an amount or a total is S1 whether or not a template hides it, because D-36 is about the response body.
  4. Anything that could spend the LINE allowance is at least S2 — a send inside a transaction, a broadcast, a per-tenant push for an announcement, or test mode defaulting off (D-34, R-02). There is no second pool of 500 messages.

Defect found while writing this pipeline · S2 · CI

Spec §6.5.3 runs npm run db:migrate before the printf that creates .env.test, and its own note explains the printf as a fix for npm test's missing env file. But db:migrate is node --env-file=.env db/reset.js --schema-only — it reads .env, not .env.test, and CI never writes .env at all. Node exits ENOENT on the db:migrate step, so the schema gate never runs. The workflow above writes both files as the first step after npm ci; the fix is one step moved and one file added.

Four things this pipeline deliberately does not have: a coverage gate (ADR §6.9), a matrix over Node versions (the project pins one), a deploy step (Render auto-deploys on green main), and any secret. Every value above is the literal string ci-only-not-a-secret, which is safe precisely because LINE_MOCK=1 means no credential is ever used against a real endpoint.

// Asia/Bangkok is UTC+7 with no DST, so a fixed offset is exact and needs no library.
// These are deliberately an INDEPENDENT implementation of the product's date rules:
// if the two disagree, one of them is wrong, and that is the point of an oracle.

export const todayBangkok = (): string =>
  new Date(Date.now() + 7 * 3_600_000).toISOString().slice(0, 10);

export const currentPeriod = (): string => todayBangkok().slice(0, 7);

export const addDays = (iso: string, n: number): string =>
  new Date(Date.parse(iso + 'T00:00:00Z') + n * 86_400_000).toISOString().slice(0, 10);

/**
 * D-20: due_date = MAX(due day of the period month, approval date + 3 days).
 * The clamp applies to the DAY-OF-MONTH term only — never to the result of the MAX,
 * which would otherwise be able to produce a due date before the three-day floor.
 * See the S3 documentation defect raised in the strategy section.
 */
export function expectedDueDate(period: string, dueDay = 5, approvedOn = todayBangkok()): string {
  const [y, m] = period.split('-').map(Number);
  const lastDayOfMonth = new Date(Date.UTC(y, m, 0)).getUTCDate();
  const onDueDay = `${period}-${String(Math.min(dueDay, lastDayOfMonth)).padStart(2, '0')}`;
  const floor = addDays(approvedOn, 3);
  return onDueDay > floor ? onDueDay : floor;   // ISO dates compare correctly as strings
}

// LINE messages and the receipt use the full Thai month with a GREGORIAN year.
// The -u-ca-gregory keyword is load-bearing: plain th-TH renders Buddhist Era (D-03).
export const thaiFullDate = (iso: string): string =>
  new Intl.DateTimeFormat('th-TH-u-ca-gregory-nu-latn', {
    timeZone: 'Asia/Bangkok', day: 'numeric', month: 'long', year: 'numeric',
  }).format(new Date(iso + 'T12:00:00+07:00'));

// REC-<payment month YYYYMM>-<6 digits>. The month comes from the RUN DATE, never
// from a literal: D-44 forbids any test asserting the documentation's 202609.
export const receiptNo = (seq: number, on = todayBangkok()): string =>
  `REC-${on.slice(0, 4)}${on.slice(5, 7)}-${String(seq).padStart(6, '0')}`;

import { test as base, expect } from '@playwright/test';
import { createConnection, type Connection } from 'mysql2/promise';
import { readFileSync, writeFileSync, existsSync } from 'node:fs';

export type OutboxEntry = { api: 'push' | 'multicast' | 'reply'; to?: string; msg: any; key?: string };

class Db {
  constructor(private readonly c: Connection) {}

  static async open() {
    // dateStrings mirrors db/pool.js so a DATE never passes through a JS Date (ADR A-5).
    const c = await createConnection({
      uri: process.env.DATABASE_URL,
      multipleStatements: true,
      dateStrings: true,
      timezone: '+07:00',
      decimalNumbers: false,          // DECIMAL arrives as a string, as in production
    });
    return new Db(c);
  }

  async rows<T = any>(sql: string, params: unknown[] = []): Promise<T[]> {
    const [r] = await this.c.query(sql, params);
    return r as T[];
  }

  async one<T = any>(sql: string, params: unknown[] = []): Promise<T> {
    const r = await this.rows<T>(sql, params);
    expect(r, `expected exactly one row for: ${sql}`).toHaveLength(1);
    return r[0];
  }

  /** Applies one idempotent .sql fixture from test/fixtures/. */
  async applyFixture(name: string) {
    await this.c.query(readFileSync(`test/fixtures/${name}`, 'utf8'));
  }

  roomId = (code: string) =>
    this.one<{ id: number }>('SELECT id FROM rooms WHERE room_code = ?', [code]).then((r) => r.id);

  billId = (roomCode: string, period: string) =>
    this.one<{ id: number }>(
      'SELECT b.id FROM bills b JOIN rooms r ON r.id = b.room_id WHERE r.room_code = ? AND b.period = ?',
      [roomCode, period],
    ).then((r) => r.id);

  items = (billId: number) =>
    this.rows('SELECT item_type, quantity, unit_price, amount FROM bill_items WHERE bill_id = ? ORDER BY item_type', [billId]);

  notifications = (billId: number) =>
    this.rows('SELECT type, status, attempt_count, recipient_user_id FROM notifications WHERE bill_id = ? ORDER BY id', [billId]);

  close = () => this.c.end();
}

class Outbox {
  private readonly path = process.env.LINE_OUTBOX_FILE ?? '.tmp/line-outbox.jsonl';

  truncate() { writeFileSync(this.path, ''); }

  all(): OutboxEntry[] {
    if (!existsSync(this.path)) return [];
    return readFileSync(this.path, 'utf8').split('\n').filter(Boolean).map((l) => JSON.parse(l));
  }

  /** The rendered Thai text of every message sent so far. */
  texts(): string[] { return this.all().map((e) => e.msg?.text ?? ''); }

  /** Polls the file — the send happens after the response, so it can land a beat late. */
  async waitForText(needle: string, timeoutMs = 15_000): Promise<string> {
    const deadline = Date.now() + timeoutMs;
    while (Date.now() < deadline) {
      const hit = this.texts().find((t) => t.includes(needle));
      if (hit) return hit;
      await new Promise((r) => setTimeout(r, 250));
    }
    throw new Error(`no LINE message containing "${needle}" after ${timeoutMs}ms. Sent: ${JSON.stringify(this.texts())}`);
  }
}

// test/helpers/client.js — session cookie + CSRF, no supertest (ADR A-9)
const BASE = process.env.TEST_BASE_URL ?? 'http://127.0.0.1:3000';

export async function login(role) {
  const jar = { cookie: '', csrf: '' };
  const keep = (res) => {
    const set = res.headers.getSetCookie?.() ?? [];
    if (set.length) jar.cookie = set.map((c) => c.split(';')[0]).join('; ');
    return res;
  };

  // The token is issued on GET and read out of the form's hidden input.
  const form = await keep(await fetch(`${BASE}/login`, { headers: { cookie: jar.cookie } }));
  jar.csrf = /name="_csrf"\s+value="([^"]+)"/.exec(await form.text())[1];

  const password = role === 'admin'
    ? process.env.SEED_ADMIN_PASSWORD
    : process.env.E2E_STAFF_PASSWORD ?? process.env.SEED_ADMIN_PASSWORD;

  await keep(await fetch(`${BASE}/login`, {
    method: 'POST', redirect: 'manual',
    headers: { cookie: jar.cookie, 'content-type': 'application/x-www-form-urlencoded' },
    body: new URLSearchParams({ username: role, password, _csrf: jar.csrf }),
  }));
  return jar;
}

/** JSON call. Returns { status, body } so a test can assert both halves of a failure. */
export async function api(jar, method, path, payload) {
  const res = await fetch(BASE + path, {
    method,
    headers: {
      cookie: jar.cookie,
      'content-type': 'application/json',
      'X-CSRF-Token': jar.csrf,
    },
    body: payload === undefined ? undefined : JSON.stringify(payload),
  });
  return { status: res.status, body: await res.json().catch(() => null) };
}

Unit tests — the formulas, the rollover and rate resolution

Which half of a formula a unit test can prove

Each of the three formulas has two halves. The quantity half — current − previous, and the room's snapshotted area — is pure JavaScript and is unit-tested below. The money half — ROUND(quantity × unit_price, 2) — is executed by MySQL on DECIMAL (D-16, A-4), so no unit test can reach it; reimplementing it in JavaScript would be testing the test.
