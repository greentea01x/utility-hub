Rooms, Tenants & Meter Readings

Sixty-nine executable test cases covering the master data every later screen reads and the reading round that turns it into money: Rooms (ห้องพัก), Tenants (ผู้เช่า) and Meter Reading (จดมิเตอร์). Everything downstream — the bill, the receipt, the LINE message — is a snapshot of a value entered on one of these three screens, so a defect here is silent and permanent: it does not crash, it charges the wrong number and prints it.

Each case is written to be run by one person against the seed.sql fixture of D-44 with a stopwatch and a browser, and every expected value is exact. Where a case is an API case the request is the endpoint from the engineering specification §3.2–§3.3 verbatim; where it is a UI case the copy is the Thai string from the UI design verbatim. A case that says "422 READING_BELOW_PREVIOUS" fails if the response is a 400, a 409, or a 422 carrying a different code.

Priority
P0 demo-critical or touches money · P1 core correctness, validation, permissions · P2 polish and rare edges.
Type
unit = a pure function or a single SQL expression · API = one HTTP request and its response body · UI = one screen and its rendered copy · e2e = a sequence crossing at least two screens or two roles.
Sessions
"Admin" = a session for user id 1, "Staff" = a session for user id 2, "anonymous" = no session cookie at all.
Dates
Written on the documentation calendar (period 2026-09, today 7 ก.ย. 2026). On a live run seed.sql computes every date relative to the run date (D-44) — reproduce the arithmetic, never the calendar.
Assumptions recorded by this section
  1. Room 205's tenant is อารยา ศรีสุวรรณ · 0812345678 · LINE display name Araya, following the UI design, which declares that cast binding for every chapter. The engineering specification's fixture table (§3.1.10) labels tenant id 37 "สมชาย ใจดี", who is room 202's tenant in the same UI design. The id (37) and the phone number are consistent across both documents; only the name differs. Tests assert on the id and on tenant_name_snapshot being stable rather than on a literal name, so this section passes under either reading — but the two documents should be reconciled.
  2. The binding floor range is 1–99 (spec §3.3.3). The room form's validation table says 1–127, which is the raw TINYINT range, not a product rule. TC-ROOM-007 asserts 1–99 and treats 100 as rejected.
  3. New rooms created by a test use codes outside the seed's 101–516 block — 517 and 518. The UI design's example toast "เพิ่มห้อง 209 แล้ว" uses a code the seed already occupies; it is an illustration, not a fixture.
  4. An out-of-range room area is rejected at the same boundary in the form and in the API (> 0 and ≤ 9999.99). The specification gives the range; the form gives the Thai sentence. Neither states which layer rejects first, so both are asserted.
  5. Room deactivation is reversible via เปิดใช้งานอีกครั้ง, per the room detail's success banner. No decision states the button's endpoint, so TC-ROOM-018 asserts the banner and the exclusion behaviour, not a route.

2. Rooms — Occupied/Vacant status, deactivation and deletion

Room status is the switch that decides whether a room is billed at all (D-07). It is derived, never entered, and no screen in the product offers a control for it. These seven cases prove that the only two writers of rooms.status are the tenant transactions, and that a room carrying history can be retired but never erased.
