Authentication, Users, Roles & Settings

Seventy executable test cases covering the gate and the control room of Juristic Platform: sign-in and session lifetime, the two-role permission matrix on every page and endpoint group, the Users page, and the four Settings forms whose values decide what a future bill costs and what a receipt prints. Cases are grouped by feature; ids run TC-AUTH-001 … TC-AUTH-070 in one continuous sequence, so an id never moves when a group grows.

How to read a case

Type — unit (pure function, no database), API (one HTTP request against a scratch schema, asserting status, error code and payload), UI (one rendered screen, asserting Thai copy, field state and test hooks), e2e (a sequence across screens, ending in a persisted effect). Priority — P0 demo-critical or money-touching, P1 must pass before submission, P2 completeness. Every expected result states an exact value: an HTTP status, an UPPER_SNAKE error code, a Thai sentence copied verbatim from the design, or an amount in the 1,790.00 form. Thai copy is asserted character for character — an extra space is a failure, because the same strings print on a receipt and reach a tenant's phone.

0. Fixture, environment and preconditions common to every case

Unless a case says otherwise, the database is rebuilt from db/schema.sql + db/seed.sql immediately before the case runs, the process runs with TZ=Asia/Bangkok, MySQL runs at time_zone='+07:00', and settings.line_test_mode = 1 so no message can reach a real phone (D-34, D-44).

Four contradictions between the source documents, and how these tests resolve them

Each resolution is a QA decision, not an invention; the losing variant is recorded here so the owning author can correct their document.

  1. Inactive account message. Engineering spec §3.3.1 and the error catalogue make wrong password, unknown username and Inactive user indistinguishable (LOGIN_INVALID · ชื่อผู้ใช้หรือรหัสผ่านไม่ถูกต้อง); UI design §1 gives the Inactive case its own banner บัญชีนี้ถูกปิดการใช้งาน. Tests follow the spec — it is the binding rules document and the security-conservative option (no account enumeration). TC-AUTH-006 asserts the shared message and flags the design's banner as a documentation defect to reconcile.
  2. Forced first-password change. D-37 states that "first login forces a change", which reads as a gate; the ADR's users table carries no must_change_password column to drive one, and engineering spec §3.7(8) resolves the wording explicitly — the rule is realised as GET/POST /password plus a runbook step and a Dashboard banner, not as a forced redirect. The UI design has no /password/change screen and no forced-change state, so it agrees with the spec. Tests follow the ADR and spec: TC-AUTH-019…021 exercise /password with current_password. No test asserts a forced-redirect flow, and none may be written unless a column is added to the schema first.
  3. Duplicate-username message. Spec catalogue: ชื่อผู้ใช้นี้ถูกใช้แล้ว. UI design: ชื่อผู้ใช้นี้มีอยู่แล้ว. Tests assert the spec string (§3.1.6 declares itself exhaustive); TC-AUTH-037 records the design variant.
  4. Failed-login HTTP status. Spec §3.3.1 says the page surface re-renders with 200; the error catalogue maps LOGIN_INVALID to 401. Tests assert the page contract — re-render with the Thai banner, no Set-Cookie session, values preserved — and treat 200 (page) / 401 (JSON) as the two surfaces of one rule.
Assumptions recorded by this section
  1. Session assertions inspect the sessions table directly, because express-mysql-session is the only durable evidence that a session was created or destroyed; there is no GET /api/me to ask (spec §3.1.3).
  2. "No amount appears in a Staff response body" is asserted mechanically: the response text is searched for /\d{1,3}(,\d{3})*\.\d{2}/ and for the strings บาท, unit_price, total, amount. A hit is a failure even when the number is unrelated (ADR §6.9, D-36).
  3. Rate-resolution and due-date cases are written as unit tests over fixtures because both are pure functions of (period, rows) and (due_day, approval_date); the e2e cases that follow each one prove the same rule through HTTP.
  4. The demo calendar (5 ก.ย. 2026, 3 ก.ย. 2026, REC-202609-000852) is used as documentation values. Where a case depends on "today", it pins the clock or computes the expectation from CURDATE(), per D-44: reproduce the arithmetic, never the calendar.
  5. The login rate limiter is exercised with the limiter store reset between cases; otherwise ten earlier failures in one file would poison the next case.
