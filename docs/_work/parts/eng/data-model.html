Data Model & Database

Eighteen tables on MySQL 8.4 (minimum 8.0.16 for CHECK), InnoDB, utf8mb4 throughout, accessed through mysql2/promise with hand-written prepared statements and no ORM (ADR §1, A-2). The schema is not a transcription of the object graph — it is where the rules that cost money live. Eleven unique keys, three stored generated columns and twenty-one CHECK constraints hold under a race, under a handler that forgot a guard, and under a student running an UPDATE by hand (ADR §6.8 layer 4, A-10).

Schema management
Committed db/schema.sql + db/seed.sql, database rebuilt from empty. No migration framework, no schema_migrations (ADR A-3).
Surrogate key
id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT on every table except counters (name), line_followers (line_user_id), settings (fixed id = 1) and sessions (session_id).
Money
DECIMAL(10,2) amounts, DECIMAL(8,2) rates, DECIMAL(6,2) area. FLOAT and DOUBLE appear nowhere (D-16).
Time
TIMESTAMP for instants (stored UTC, read back as Asia/Bangkok), DATE for business dates, dateStrings: true on the pool (D-03, ADR A-5).
Naming
Tables snake_case plural; columns snake_case singular; foreign keys <singular_table>_id; indexes uq_<table>_<cols> / ix_<table>_<cols>; foreign keys fk_<table>_<role>; checks ck_<table>_<rule> (ADR §6.1).
Deletion
Nothing on the money path is ever deleted. Retirement is a column, not a DELETE — see §6.6.
One deviation from the section brief, recorded rather than silently applied

The brief for this section says money is DECIMAL(12,2). D-16 is binding and says DECIMAL(10,2), and the ADR restates it in §6.4. This document uses DECIMAL(10,2). The ceiling is 99,999,999.99 THB on a single amount, against a real maximum around 3,000 THB per bill and 120,000 THB per month across 67 rooms — six orders of magnitude of headroom. No sibling section should write DECIMAL(12,2).

Eighteen tables. The billing spine carries every foreign key; five tables stand alone by design — settings is a singleton, counters holds one row, job_runs is a scheduler ledger, line_followers is keyed by LINE's own identifier, and sessions is owned by express-mysql-session.
There is no line_accounts table

PRD §21 lists LineAccounts; that entry is descriptive, not normative. D-29 keys the binding to the tenant, and tenants.id already gives that uniqueness by construction, so the binding is three columns on tenants — line_user_id, line_display_name, line_linked_at — plus link_codes for the one-time code and line_followers for the pre-binding follow event (ADR A-12). One LINE account may be bound to two Active tenants (a parent renting two rooms); every template names the room, and each room's bill writes its own notifications row.

PRD §21 also splits rates into UtilityRates and CommonAreaRates. One rates table with utility_type ENUM('water','electric','common') replaces both: the resolution query, the effective-dating rule and the Settings screen are identical for all three, and two tables would mean two copies of D-17.

There is no reading status and no period table

meter_readings has no status column and no state machine, and there is no periods table and no closed state anywhere in the system (D-11, ADR §3.4). A reading's editability is derived: editable while its room's bill for that period is Draft or does not exist, frozen otherwise (D-12). Storing it would create a second source of truth that a revert would have to keep in sync.

8. Assumptions recorded by this section

  1. Money stays DECIMAL(10,2), per D-16 and ADR §6.4, against the section brief's DECIMAL(12,2). Recorded above as a callout so a reviewer can find it.
  2. No line_accounts table and no separate CommonAreaRates table. PRD §21's list is descriptive; ADR A-12 and D-17 are normative. The LINE binding is three columns on tenants; all three rates live in one rates table.
  3. A revert clears approved_by and approved_at. D-22 does not say so explicitly; ck_bills_approved requires it, and the approval history survives in audit_log where D-38 puts it.
  4. Column widths not fixed by a decision are chosen here and are binding on sibling sections: names 120, addresses 255, reasons 200–255, last_error 255, announcements.title 60 and body 400 (the D-35 form limits), settings.office_hours 60.
  5. ck_readings_units is deliberately redundant against INT UNSIGNED. D-13 names the constraint; keeping it documents the invariant where a reader looks for it, at zero cost.
  6. REGEXP inside CHECK is used for period, phone, receipt_no, audience_floors and the link-code alphabet. It is deterministic and legal from MySQL 8.0.16. If a managed provider ever rejects one, the fallback is the same rule in the matching zod schema plus a note in the runbook — every one of these five is already validated at layer 2 (ADR §6.8).
  7. ON DELETE CASCADE appears exactly once, on fk_bill_items_bill. Bills are never deleted in production; the cascade exists so the integration tier can drop a scratch bill in one statement.
  8. audit_log.entity_id carries no foreign key because it points at four different tables. ix_audit_entity covers the lookup; bill_id, the column that actually drives a screen, is a foreign key.
  9. Sizing. 80 rooms × 12 periods ≈ 960 bills, 2,880 bill items, 1,920 readings and roughly 3,000 notification rows a year. The whole database is under 50 MB after five years, which is why no index exists that is not named in §3.12 and why partitioning, archiving and read replicas are all out of scope.
