Project Structure, Environment & Implementation Plan

This section turns ADR-001 into something a student can check out on a Monday morning and run. It fixes the folder tree, the environment variables, the npm scripts, the deploy procedure, the milestone plan for a 3–4 person team over one 14-week semester, the quality strategy and the risk register. Every name below either comes from ADR-001 §5–§6 verbatim or is listed as a new identifier in the callout at the end of this section.

Three structural facts that shape everything in this section
  • One repository, one deployable process, zero build steps (ADR A-1, D-43). The "frontend" is views/ + public/ inside the same repo. There is no second package.json, no bundler, no second deploy target, and therefore no npm run build.
  • No migration framework (ADR A-3). The database is rebuilt from a committed db/schema.sql + db/seed.sql. The script called db:migrate below applies the schema to an empty database; it does not step through versioned files.
  • The graded deliverable is the PRD §28 demo path. The milestone order below is chosen so that room 205 produces 1,790.00 THB end-to-end as early as week 8, and with LINE by week 9 — five weeks before the defence.

The layering rule, in one sentence

Routes do HTTP, services do transactions and rules and their own SQL, lib/ is pure functions. A req object never reaches a service; a SQL string never appears in a route; an arithmetic operator never appears next to money in JavaScript. These three greps are the entire code review for structure: grep -rn "req\." services/, grep -rniE "select|insert|update" routes/, grep -rn "\*\|+" lib/money.js must each return nothing.

2.2 First-time setup — six commands

  1. git clone <repo> && cd juristic-platform
  2. npm ci — installs exactly the locked versions. Never npm install on a fresh clone.
  3. cp .env.example .env then fill it in (§2.3). Generate the two secrets with node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))".
  4. mysql -u root -p -e "CREATE DATABASE juristic CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci" — utf8mb4 is not optional; Thai names and LINE message templates live in these tables.
  5. npm run db:reset — drops every table, applies db/schema.sql, then db/seed.sql. Prints 80 rooms · 67 tenants · 54 LINE-linked · rates 18.00/8.00/35.00 · due day 5. Fails loudly if SEED_ADMIN_PASSWORD is unset (D-37).
  6. npm run dev → open http://localhost:3000, log in as admin with your SEED_ADMIN_PASSWORD.
Verify the install with numbers, not with a vibe

Run npm run rehearse. It must print the PRD §28 arithmetic and exit 0:
room 205 · water 1,250 → 1,260 = 10 × 18.00 = 180.00 · electric 5,280 → 5,350 = 70 × 8.00 = 560.00 · common 30.00 × 35.00 = 1,050.00 · total 1,790.00 · receipt REC-<YYYYMM>-000852
If the total is anything other than 1,790.00, stop and fix that before writing another line of code.

2.5 Schema changes and seeding

There is no schema_migrations table and no numbered files. A schema change is an edit to db/schema.sql followed by npm run db:reset on every laptop. That is legitimate precisely because there is no production data to preserve — the only database that matters is rebuilt from seed.sql in one command.

SituationProcedure
Adding a column or indexEdit db/schema.sql, edit db/seed.sql if the column needs demo values, npm run db:reset, run npm test, commit both files in the same commit as the code that uses them.
A teammate pulls your schema changeThey run npm run db:reset. Their local data is disposable by design. The PR description says "requires db:reset" on the first line.
Changing the deployed databaseRender Shell → npm run db:migrate → npm run db:seed. Take the dump of §3.5 first if the deployed data contains a rehearsal you care about.
Real data must survive a schema changeIt never does in this project. If that changes, the trigger to add a migration runner has arrived — that is a decision, recorded as an ADR amendment, not an afternoon's improvisation.

Seed facts a test may rely on (D-44): 80 rooms across 5 floors (101–116 … 501–516), all 30.00 sqm; 67 Occupied, 13 Vacant; 67 Active tenants of which exactly 54 carry a LINE binding; rates 18.00 / 8.00 / 35.00 effective from the first day of the earliest history period; due day 5; room 205's current-period bill left Draft so the demo approves it live; the receipt counter offset so room 205's payment issues REC-<current YYYYMM>-000852. Every seed date is computed from CURDATE() — a test asserts 1,790.00, never 5 ก.ย. 2026.

2.6 Running locally against LINE

Local development never receives webhooks: the LINE console holds exactly one webhook URL and it belongs to the Render deployment (D-43). Locally, settings.line_test_mode = 1 redirects every outbound message to line_test_user_id, and inbound linking is exercised in two ways — the integration tests post a signed fake message event to POST /line/webhook with a body signed by LINE_CHANNEL_SECRET, and the deployed instance is used for the one real end-to-end link per milestone. No tunnel, no ngrok, no second webhook URL.

3.2 Deploy procedure — first time

  1. Aiven. Create a free MySQL 8.4 service, region Singapore. Copy the service URI. Create the database: CREATE DATABASE juristic CHARACTER SET utf8mb4.
  2. Render. New → Web Service → connect the GitHub repo → Runtime Node → Build Command npm ci → Start Command npm start → free instance type. Auto-deploy on main.
  3. Environment variables. Add all nine of §2.3 in the Render dashboard. NODE_ENV=production, TZ=Asia/Bangkok, DATABASE_URL = the Aiven URI. Do not add SEED_ADMIN_PASSWORD permanently — see step 5.
  4. First deploy. Push to main. Wait for Live. curl https://<service>.onrender.com/healthz must return {"data":{"ok":true}}.
  5. Seed once. Render Shell → set SEED_ADMIN_PASSWORD for the session → npm run db:reset → confirm the printed counts → log in and change the admin password → remove the variable.
  6. LINE console. Messaging API → Webhook URL = https://<service>.onrender.com/line/webhook → Verify (must be green) → Use webhook ON → auto-reply messages OFF, greeting message ON.
  7. cron-job.org. Two separate jobs. (a) POST https://<service>.onrender.com/internal/jobs/daily, header X-Job-Token: <JOB_TOKEN>, daily at 09:00, timezone Asia/Bangkok. (b) GET https://<service>.onrender.com/healthz, every 10 minutes. These are two jobs, not one — the daily job is not a keep-alive (D-32, D-43).
  8. Smoke test on the deployed instance. Log in, open Meter Reading for room 205, save water 1,260, generate, open Bill Detail, confirm the total reads 1,790.00.

3.3 Deploy procedure — every subsequent release

  1. Merge to main only when CI is green (§5.3). Render deploys automatically.
  2. If db/schema.sql or db/seed.sql changed: take the dump of §3.5, then Render Shell → npm run db:reset.
  3. curl /healthz, then log in and load Dashboard.
  4. Re-verify the webhook URL in the LINE console — one click, and it is the single line of the runbook that has ever silently killed the linking flow (D-43).
  5. npm run rehearse against the deployed instance's database before any milestone review or the defence.

Recovery objective, stated plainly

Acceptable data loss is everything. There is no real tenant data (D-44: all seed content is fictional). The recovery target is time: a destroyed database must be back to a demonstrable state in under 10 minutes, which npm run db:reset meets. There is no APM, no error tracker and no log aggregation. Render keeps the last logs, MySQL keeps job_runs, notifications and audit_log, and those three tables answer every operational question this system can be asked.

5.2 The one test that may never go red

test('PRD 28 demo arithmetic', async () => {
  const bill = await generateFor({ room: '205', period: '2026-09' });
  assert.equal(bill.items.water.quantity, '10');       // 1,260 - 1,250
  assert.equal(bill.items.water.amount, '180.00');     // 10 x 18.00
  assert.equal(bill.items.electric.quantity, '70');    // 5,350 - 5,280
  assert.equal(bill.items.electric.amount, '560.00');  // 70 x 8.00
  assert.equal(bill.items.common.amount, '1050.00');   // 30.00 x 35.00
  assert.equal(bill.total, '1790.00');                 // sum of the printed lines
});

Every value is a string, because mysql2 returns DECIMAL as a string and no amount ever passes through a JavaScript float (D-16). A test that compares to a number is a test that will pass while the receipt prints 1789.9999999999998.

5.4 Definition of done

A task is done when every line below is true. Not "mostly", and not "the happy path".

  • The feature works against db/seed.sql, not against three rows typed by hand.
  • Every visible string is Thai; every route, filename and data-status value is the English identifier (D-02).
  • Money is formatted by lib/money.js and computed in SQL. No *, + or toFixed touches an amount in JavaScript.
  • The failure path renders: 422 shows the Thai inline message with the typed values preserved; 403 shows the Thai page with the button back to จดมิเตอร์ (D-40).
  • Anything that changes money or bill state writes its audit_log row on the same connection, inside the same transaction (D-38).
  • A unit test exists for any calculation, and an integration test exists for any state transition.
  • npm run lint and npm test are green locally, and CI is green on the branch.
  • The PR description names the decision ids it implements and says "requires db:reset" when the schema or seed changed.
  • A second student has pulled the branch, run npm run db:reset and clicked the feature once.
  • It introduces nothing from the PRD §24 exclusion list — no rent, no lease, no gateway, no slip, no QR, no IoT, no AI.
