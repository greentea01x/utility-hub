Billing Engine & Business Rules

Everything that turns two meter numbers into an amount a tenant owes, and everything that happens to that amount afterwards. Every rule cites the decision (D-xx) it comes from and carries a worked example with full arithmetic. Where a rule needs SQL, the SQL is the specification — JavaScript never multiplies, sums or rounds money (D-16, ADR A-4).

Where these rules live in the code

services/billing.js, services/payment.js, services/jobs.js, services/reports.js, plus the pure helpers lib/billStatus.js, lib/datetime.js and lib/money.js. Routes parse and redirect; services own transactions, rules and their own SQL; lib/ is pure functions (ADR §5, A-7). A req object never reaches a service and a SQL string never appears in a route.

1. The billing period and month selection

A billing period is the billing month: a plain CHAR(7) YYYY-MM string stored on meter_readings.period and bills.period (D-11). There is no periods table, no Admin "open period" action, no lock and no closed state — the word does not appear in this document set, in any screen or in any test.

  • Selection. Meter Reading and Monthly Billing each carry one month picker defaulting to the current calendar month in Asia/Bangkok: DATE_FORMAT(CURDATE(), '%Y-%m'). It is passed as ?period=YYYY-MM and validated by zod against /^\d{4}-(0[1-9]|1[0-2])$/; anything else is 422 PERIOD_INVALID.
  • Ordering. CHAR(7) string order is chronological, so ORDER BY period DESC is both correct and index-friendly, and "strictly earlier period" is period < ? (D-14).
  • Period first day. The derived value CONCAT(period, '-01') is used by rate resolution and by the due-date rule. It is referred to below as the period first day.
  • Coverage. The consumption a period bills is whatever accrued since that room's previous reading, which is not guaranteed to be the previous calendar month (D-14). Periods need not be contiguous and a gap never blocks a run.
  • Protection. Data is protected by bill status, not by a period state machine: a reading is editable exactly while its room's bill for that period is ฉบับร่าง or does not yet exist (D-12, §7 below).
  • Progress is shown, not stored. Monthly Billing renders one derived line for the selected period: บิลครบทุกห้อง {billed}/{billable} · อนุมัติแล้ว {approved} · ชำระแล้ว {paid} (D-11).

2. Rate resolution

rates is append-only and effective-dated; a Settings save INSERTs and never UPDATEs (D-17). Resolution is keyed to the period, never to the moment Generate was pressed, so a late second run cannot put two electricity rates in one month.

-- billing.resolveRate(utilityType, periodFirstDay)
SELECT unit_price
  FROM rates
 WHERE utility_type = ?                       -- 'water' | 'electric' | 'common'
   AND effective_from <= ?                    -- CONCAT(period, '-01')
 ORDER BY effective_from DESC
 LIMIT 1;

Three rates are resolved once per generation run, before the room loop. If any of the three returns no row the whole run is refused with 422 RATE_NOT_FOUND and nothing is written — a run that silently priced water at zero would be worse than a run that did not happen. The resolved unit_price is copied onto the bill_items row next to the quantity, and every screen, print view and LINE message renders from that snapshot (D-09, D-17). Approved bills are never disturbed by a later rate row.

Back-dating a rate into a period that already has Draft bills

Settings shows มีบิลฉบับร่าง {N} ใบในรอบนี้ ยังใช้อัตราเดิมอยู่ with the button คำนวณบิลฉบับร่างใหม่ → POST /settings/rates/recalculate-drafts, which calls billing.recalculateBill() for Draft bills only (D-17). Approved bills are untouched by construction: recalculateBill() carries AND status = 'Draft' in every statement it issues.

3. Previous-reading resolution

One code path, no special cases (D-06, D-14). Opening readings live on rooms.baseline_water / rooms.baseline_electric; no synthetic meter_readings row is ever written, so nothing can collide with a room's first real reading under uq_readings(room_id, period, utility_type).

-- billing.resolvePreviousReading(roomId, utilityType, period)
SELECT current_reading, period
  FROM meter_readings
 WHERE room_id = ? AND utility_type = ? AND period < ?    -- strictly earlier
 ORDER BY period DESC
 LIMIT 1;

-- no row  ->  previous_reading = rooms.baseline_<utility>, previous_period = 'baseline'

When the resolved previous_period is not the immediately preceding month, Bill Detail shows ครอบคลุมการใช้ตั้งแต่รอบ {previous_period_th} and the BILL LINE message appends the same sentence (D-14, D-31). Units are never split or back-dated across the skipped months and no bill is created for a skipped period.

4. Formulas and rounding

units_water = current_reading − previous_reading (INT UNSIGNED, CHECK units >= 0)
units_electric = current_reading − previous_reading
units (meter replaced) = (old_final − previous_reading) + (current_reading − new_start)

amount_water = ROUND(units_water × rate_water, 2)
amount_electric = ROUND(units_electric × rate_electric, 2)
amount_common = ROUND(area_sqm × rate_common, 2)

bills.total = amount_water + amount_electric + amount_common (SQL SUM of the already-rounded items)

5. The generation algorithm

Trigger (D-18): the Meter Reading page's primary action ส่งให้นิติตรวจสอบ (Staff and Admin), enabled once at least one room in the period has both readings; Admin may re-run any time from Monthly Billing via สร้าง/อัปเดตบิลฉบับร่าง. Both call POST /api/bills/generate. There is no separate "submitted" state — running generation is the submission.

flowchart TB
  S["Run generation for period P"] --> R["Resolve the three rates at the period first day"]
  R --> L["List billable rooms"]
  L --> N{"Both readings saved?"}
  N -->|no| U["count unread, write nothing"]
  N -->|yes| B{"Bill for this room and P?"}
  B -->|none| C["INSERT Draft bill with snapshots"]
  B -->|"Draft"| K["keep the row, recalculate in place"]
  B -->|"Unpaid or Paid"| SK["count skipped, touch nothing"]
  C --> I["UPSERT exactly three bill_items"]
  K --> I
  I --> T["UPDATE total to the SUM of the items"]
  T --> Z["summary: created, updated, skipped, unread"]
  U --> Z
  SK --> Z
One run, one transaction per room. Steps that write are the only ones that can fail, and a failure isolates to a single room.

5.1 The billable-room query (D-07, ENG-1)

-- billing.billableRooms(conn)
SELECT r.id AS room_id, r.room_code, r.area_sqm,
       t.id AS tenant_id, t.full_name AS tenant_name
  FROM rooms r
  JOIN tenants t ON t.active_room_id = r.id     -- generated column, UNIQUE (ENG-1)
 WHERE r.is_active = 1
   AND r.status = 'Occupied'
 ORDER BY r.room_code;

Because tenants.active_room_id is a stored generated column with a unique index, this join returns at most one tenant per room — there is no LIMIT 1 that could silently pick the wrong tenant. A room that is Vacant, deactivated, or has no Active tenant is not in the result set and therefore has no bill, no reading requirement, no common-area fee and no LINE recipient (D-07).

5.2 Pseudo-code

// services/billing.js
async function generatePeriod(period, actor) {
  assertPeriod(period);                               // 422 PERIOD_INVALID
  const first = period + '-01';                       // the period first day
  const rate = {
    water:    await resolveRate('water',    first),
    electric: await resolveRate('electric', first),
    common:   await resolveRate('common',   first),
  };
  if (!rate.water || !rate.electric || !rate.common) throw AppError(422, 'RATE_NOT_FOUND');

  const dueDay  = await settings.dueDay();            // 1..28, CHECK-enforced
  const summary = { period, created: 0, updated: 0, skipped: 0, unread: 0 };

  for (const room of await billableRooms()) {
    await withTx(async (conn) => {
      const r = await readingsFor(conn, room.room_id, period);   // { water?, electric? }
      if (!r.water || !r.electric) { summary.unread++; return; } // D-23: no bill, no placeholder

      // Serialise concurrent runs on this room; uq_bills(room_id, period) is the backstop.
      let bill = await selectBillForUpdate(conn, room.room_id, period);

      if (bill && bill.status !== 'Draft') { summary.skipped++; return; }   // D-18 rule 3

      if (!bill) {
        bill = await insertDraftBill(conn, {                    // snapshots, D-09
          room_id: room.room_id, tenant_id: room.tenant_id, period,
          room_code_snapshot: room.room_code,
          room_area_sqm:      room.area_sqm,
          tenant_name_snapshot: room.tenant_name,
          status: 'Draft', total: '0.00',
          due_date: draftDueDate(period, dueDay),               // preview only, D-20
        });
        summary.created++;
      } else {
        summary.updated++;
      }

      await upsertItem(conn, bill.id, 'water',    r.water.units,    rate.water,    r.water);
      await upsertItem(conn, bill.id, 'electric', r.electric.units, rate.electric, r.electric);
      await upsertItem(conn, bill.id, 'common',   room.area_sqm,    rate.common,   null);
      await refreshTotal(conn, bill.id);
    });
  }
  return summary;      // { period, created, updated, skipped, unread }
}

5.3 The three writes, in SQL

-- (a) the Draft bill, with its three snapshot columns and the preview due date
INSERT INTO bills (room_id, tenant_id, period, room_code_snapshot, room_area_sqm,
                   tenant_name_snapshot, total, status, due_date)
VALUES (?, ?, ?, ?, ?, ?, 0.00, 'Draft',
        LEAST(DATE_ADD(CONCAT(?, '-01'), INTERVAL ? - 1 DAY),
              LAST_DAY(CONCAT(?, '-01'))));

-- (b) one item, three times per bill: water, electric, common.
--     uq_bill_items(bill_id, item_type) makes a fourth or duplicate item impossible (ENG-2).
INSERT INTO bill_items (bill_id, item_type, quantity, unit_price, amount,
                        previous_reading, current_reading, previous_period)
VALUES (?, ?, ?, ?, ROUND(? * ?, 2), ?, ?, ?) AS new
ON DUPLICATE KEY UPDATE
  quantity         = new.quantity,
  unit_price       = new.unit_price,
  amount           = new.amount,
  previous_reading = new.previous_reading,
  current_reading  = new.current_reading,
  previous_period  = new.previous_period;

-- (c) the total is a SUM of already-rounded rows, never a JS addition (D-16)
UPDATE bills b
   SET b.total = (SELECT SUM(bi.amount) FROM bill_items bi WHERE bi.bill_id = b.id)
 WHERE b.id = ? AND b.status = 'Draft';

The common item carries quantity = bills.room_area_sqm and previous_reading, current_reading, previous_period all NULL. Exactly three items are always written, even at 0 units and 0.00 (D-18, D-41) — that is what makes the Dashboard tiles sum to the billed total, the receipt print three lines, and D-42's split columns never null. A bill with fewer than three items is a defect with its own assertion.

5.4 Idempotency

uq_bills(room_id, period) is the idempotency key of the entire run (D-18). The three rules, stated so they can be tested one at a time:

  1. A run creates a Draft bill for every billable room that has both readings and no bill.
  2. A run recalculates in place every existing Draft bill for the period — the row keeps its id, so audit rows, notification rows and links to it survive.
  3. A run never touches a bill whose stored status is Unpaid or Paid. It is counted in skipped and no statement is issued against it.

There is no delete-and-recreate path anywhere in the engine, because such a path could destroy an approved bill. Two operators pressing Generate simultaneously are serialised by SELECT … FOR UPDATE; if the row is created between the SELECT and the INSERT, the unique key raises ER_DUP_ENTRY, the service re-reads the row and counts it as updated.

Whenever unread > 0, Monthly Billing shows the persistent warn callout ยังไม่ได้จดมิเตอร์ {N} ห้อง: 108, 312, 405 — ยังไม่ได้สร้างบิล with the room codes linking to Meter Reading (D-23). Approval is never blocked by missing rooms.

The consequence, stated plainly

The 2026-10 bill covers consumption from 12 ก.ย. to the October reading, which includes the 12–16 ก.ย. window when the room was vacant, and the incoming tenant pays a full common-area fee for a month they occupied from the 16th. That is the documented no-proration limitation, not a defect (D-05 limitation 1, D-08). What blocks step 5 if it is attempted early: สิ้นสุดสัญญาเช่า is refused unless (a) a final reading exists for both utilities for that room dated on or after the last period the room was billed for, and (b) the bill covering that reading exists and is Paid. Without this gate the departing tenant's last month would be skipped by the run — the room would be Vacant on the generation date — and silently charged to the next tenant (D-08).

7. Reading submission and review — what is locked when

There is exactly one gate in the whole engine (D-19). Reviewing the readings and approving the bill are the same act; there is no separate reading-approval step and no submitted state.

9.2 Correcting a Paid bill (D-25, D-22)

A counter transaction, not a system transaction. The cash goes back across the counter first — the confirm dialog says so: คืนเงินสด {total} บาท ให้ผู้เช่าก่อนยืนยันการยกเลิก, with the reason field required before the primary button enables (D-39).

UPDATE payments SET voided_at = CURRENT_TIMESTAMP, voided_by = ?, void_reason = ?
 WHERE bill_id = ? AND voided_at IS NULL;          -- 0 rows -> 409 PAYMENT_NOT_FOUND
UPDATE receipts SET voided_at = CURRENT_TIMESTAMP WHERE payment_id = ?;
UPDATE bills   SET status = 'Unpaid' WHERE id = ? AND status = 'Paid';
-- audit(conn, { action: 'PAYMENT_VOID', bill_id, reason })
  • Nothing is deleted. The receipt keeps its number, and every view and print of it is stamped ยกเลิก in red across the header (D-25, D-27).
  • payments.active_bill_id becomes NULL, which frees the UNIQUE(active_bill_id) slot so the bill can be paid again later. A plain UNIQUE(bill_id) would make a corrected bill unpayable forever — this mechanism is binding (D-26).
  • The bill returns to Unpaid and therefore displays as เกินกำหนด automatically if the due date has passed.
  • No LINE message is sent on the void itself — the office explains in person.
  • The bill is thereafter excluded from automatic PRE_DUE and OVERDUE sends and shows the badge ระงับการแจ้งเตือนอัตโนมัติ (D-25, D-33). Admin's per-bill manual resend still works.
  • Re-payment issues a new receipt number; the old one stays taken. The corrected LINE message carries ยอดที่ชำระไว้เดิมได้คืนเป็นเงินสดแล้ว กรุณาชำระตามยอดใหม่ (D-22, D-31).

-- 3. receipt number, atomic and connection-local

  ON DUPLICATE KEY UPDATE seq = LAST_INSERT_ID(seq + 1);
SELECT LAST_INSERT_ID();          -- e.g. 852

-- 4. REC- + payment month YYYYMM + '-' + String(seq).padStart(6, '0')  ->  REC-202609-000852
INSERT INTO receipts (payment_id, receipt_no, issued_at) VALUES (?, ?, CURRENT_TIMESTAMP);

Step 4 is string formatting, not arithmetic, so it is the one receipt-number operation that lives in JavaScript. The counter is continuous and never resets — the YYYYMM is a label, not a scope, which is the only way a 67-room building reaches 852 (D-27). The sequence is unique and monotonic but not gapless: a rolled-back transaction consumes a number and the seed starts at an offset. No document, rationale or test may claim gaplessness; the two assertions are that no two receipts share a number and that a later payment never receives a lower one.

After the commit the queued PAID notification is pushed: ✅ ยืนยันการชำระเงิน / ห้อง 205 / ได้รับชำระค่าใช้จ่ายจำนวน 1,790 บาท เรียบร้อยแล้ว / วันที่ 3 กันยายน 2026 / เลขที่ใบเสร็จ REC-202609-000852 (D-31). Note the money format: 1,790.00 on the receipt, 1,790 บาท in the message (D-03).

Partial payment does not exist

A tenant who is short is asked to return with the full amount; the bill stays รอชำระ or เกินกำหนด (D-05 limitation 2, D-24). Because the amount always equals the total, overpayment cannot exist, no SUM appears in any payment query, and no fifth status is needed — which is precisely what lets §9.2 be a plain void with no refund machinery.

11. Overdue, the daily scheduler and the reminder rule

11.1 Overdue is derived, never stored (D-21)

bills.status stores only Draft, Unpaid, Paid. The fourth value is produced by one helper in two languages and nowhere else:

CASE WHEN b.status = 'Unpaid' AND b.due_date < CURDATE()
     THEN 'Overdue' ELSE b.status END AS display_status
export const billStatus = (b) =>
  b.status === 'Unpaid' && b.due_date < todayBangkok() ? 'Overdue' : b.status;

The transition is instantaneous at 00:00 Asia/Bangkok on the day after the due date: no job, no drift, nothing to fail, and no late fee, interest or penalty of any kind. Any surface that shows a status to a human, or filters or counts by a status a human can see, goes through the helper; aggregation that deliberately means "approved" (§12's money tiles) or "not yet settled" (§13's arrears report) reads the stored column directly and is not a violation — D-21 is a display rule. Every element rendering a status carries data-status="Draft|Unpaid|Paid|Overdue" (D-02).

11.2 The daily scheduler (D-32)

POST /internal/jobs/daily, authenticated by X-Job-Token, called at 09:00 Asia/Bangkok by an external scheduler. No node-cron: an in-process timer never fires on a sleeping free instance. The 10-minute GET /healthz ping is a separate schedule and is not this job's business (D-43).

  1. INSERT INTO job_runs (job_name, run_date, started_at) VALUES ('daily', CURDATE(), NOW()). A duplicate-key error means today already ran → 200, no-op (D-32).
  2. Queue PRE_DUE rows for every eligible bill where DATEDIFF(due_date, CURDATE()) = 2.
  3. Queue OVERDUE rows where DATEDIFF(CURDATE(), due_date) IN (1, 8, 15).
  4. SELECT GET_LOCK('notif_drain', 0), then drain queued rows and retry failed rows with attempt_count < 3, including anything a bulk approval left behind (D-19). Released in a finally.
  5. UPDATE job_runs SET finished_at, summary_json and return the counts.
-- the eligibility predicate, shared by steps 2 and 3
SELECT b.id, b.tenant_id, b.total, b.due_date, b.room_code_snapshot
  FROM bills b
  JOIN tenants t ON t.id = b.tenant_id
 WHERE b.status = 'Unpaid'                          -- stored status: excludes Draft and Paid
   AND NOT EXISTS (SELECT 1 FROM payments p         -- D-25: a voided payment suppresses the chase
                    WHERE p.bill_id = b.id AND p.voided_at IS NOT NULL)
   AND <the day condition for this message type>;

Settings carries the Admin button รันงานแจ้งเตือนตอนนี้, which calls the identical code path with job_name = 'daily_manual', skips the job_runs guard entirely so a 14:00 demo still works after the 09:00 cron ran, and relies on the notification dedupe key for safety. It reports ส่งแจ้งเตือนก่อนครบกำหนด {a} ราย · เลยกำหนด {b} ราย · ส่งซ้ำที่ล้มเหลว {c} ราย (D-32). The job never writes a bill status.

Each is a page under /reports/… and each accepts ?format=csv, producing UTF-8 with a BOM through lib/csv.js with the filename pattern report-{name}-{period}.csv (D-42). No PDF export, no report builder, no ad-hoc column chooser.

Report 1 — สรุปการเรียกเก็บและรับชำระรายเดือน. One row per period: billed, collected, outstanding, each split water / electricity / common fee, plus bill counts by status.

SELECT b.period,
       SUM(CASE WHEN b.status IN ('Unpaid','Paid') THEN b.total    ELSE 0 END) AS billed,
       SUM(CASE WHEN b.status =  'Paid'            THEN b.total    ELSE 0 END) AS collected,
       SUM(CASE WHEN b.status =  'Unpaid'          THEN b.total    ELSE 0 END) AS outstanding,
       SUM(CASE WHEN b.status IN ('Unpaid','Paid') THEN s.water    ELSE 0 END) AS water_billed,
       SUM(CASE WHEN b.status IN ('Unpaid','Paid') THEN s.electric ELSE 0 END) AS elec_billed,
       SUM(CASE WHEN b.status IN ('Unpaid','Paid') THEN s.common   ELSE 0 END) AS common_billed,
       SUM(b.status = 'Draft')  AS n_draft,
       SUM(b.status = 'Unpaid') AS n_unpaid,
       SUM(b.status = 'Paid')   AS n_paid
  FROM bills b
  LEFT JOIN (SELECT bill_id,                     -- one row per bill: the join must not fan out
                    SUM(CASE WHEN item_type = 'water'    THEN amount END) AS water,
                    SUM(CASE WHEN item_type = 'electric' THEN amount END) AS electric,
                    SUM(CASE WHEN item_type = 'common'   THEN amount END) AS common
               FROM bill_items GROUP BY bill_id) s ON s.bill_id = b.id
 WHERE b.period BETWEEN ? AND ?
 GROUP BY b.period
 ORDER BY b.period DESC;

Assertions: billed − collected = outstanding on every row, and water_billed + elec_billed + common_billed = billed on every row.

Report 2 — รายการค้างชำระ. Aged into the four non-overlapping buckets of D-42, sorted by days overdue descending.

SELECT b.room_code_snapshot, b.tenant_name_snapshot, t.phone, b.period,
       b.total, b.due_date,
       DATEDIFF(CURDATE(), b.due_date) AS days_overdue,
       CASE WHEN DATEDIFF(CURDATE(), b.due_date) <=  7 THEN '1-7'
            WHEN DATEDIFF(CURDATE(), b.due_date) <= 30 THEN '8-30'
            WHEN DATEDIFF(CURDATE(), b.due_date) <= 60 THEN '31-60'
            ELSE '61+' END AS bucket
  FROM bills b
  JOIN tenants t ON t.id = b.tenant_id
 WHERE b.status = 'Unpaid'                       -- stored status, D-21 is a display rule
   AND b.due_date < CURDATE()                    -- see the reconciliation note below
 ORDER BY days_overdue DESC, b.room_code_snapshot;
Reconciling D-42's two halves — recorded interpretation

D-42 says the report covers "every Unpaid bill across all periods" and that "the four bucket counts must sum to the row count". Those cannot both hold while a not-yet-due Unpaid bill is a row, because the buckets start at day 1. Resolution: the table rows are Unpaid bills with due_date < CURDATE() — exactly the bills displaying as เกินกำหนด — so the four buckets partition the rows and both assertions pass. Nothing becomes invisible: a summary line above the table reports the residual, ยังไม่ครบกำหนด {n} ใบ · {amount} บาท, and the all-time Dashboard tile outstanding_all_periods still counts every Unpaid bill. Bills whose payment was voided remain in the report — they are genuinely unpaid — and carry the badge ระงับการแจ้งเตือนอัตโนมัติ (D-25).

Report 3 — ประวัติรายห้อง 12 เดือน. The screen the office opens when a tenant disputes a reading.

SELECT b.period,
       MAX(CASE WHEN i.item_type = 'water'    THEN i.quantity END) AS water_units,
       MAX(CASE WHEN i.item_type = 'water'    THEN i.amount   END) AS water_amount,
       MAX(CASE WHEN i.item_type = 'electric' THEN i.quantity END) AS elec_units,
       MAX(CASE WHEN i.item_type = 'electric' THEN i.amount   END) AS elec_amount,
       MAX(CASE WHEN i.item_type = 'common'   THEN i.amount   END) AS common_amount,
       b.total,
       CASE WHEN b.status = 'Unpaid' AND b.due_date < CURDATE()
            THEN 'Overdue' ELSE b.status END AS display_status,
       MAX(p.paid_at) AS paid_at, MAX(r.receipt_no) AS receipt_no
  FROM bills b
  JOIN bill_items i ON i.bill_id = b.id
  LEFT JOIN payments p ON p.active_bill_id = b.id          -- the live payment only
  LEFT JOIN receipts r ON r.payment_id = p.id AND r.voided_at IS NULL
 WHERE b.room_id = ? AND b.period BETWEEN ? AND ?
 GROUP BY b.id
 ORDER BY b.period DESC;

This report is scoped by room_id, so it deliberately spans tenancies: an outgoing tenant's bills, payments and receipts stay attached to that tenant and remain visible in the room's history (D-08). It is the only report that uses the display_status expression, because it is the only one whose status column a human reads row by row.

Report 4 — ห้องที่ใช้น้ำ/ไฟสูงสุด. Top 10 by units for the selected period, each with its own previous-month comparison.

SELECT b.room_code_snapshot, i.quantity AS units, i.amount,
       prev.quantity AS prev_units,
       i.quantity - prev.quantity AS delta_units
  FROM bills b
  JOIN bill_items i ON i.bill_id = b.id AND i.item_type = ?          -- 'water' | 'electric'
  LEFT JOIN bills pb ON pb.room_id = b.room_id AND pb.period = ?     -- the preceding period
                    AND pb.status IN ('Unpaid','Paid')
  LEFT JOIN bill_items prev ON prev.bill_id = pb.id AND prev.item_type = i.item_type
 WHERE b.period = ? AND b.status IN ('Unpaid','Paid')
 ORDER BY i.quantity DESC
 LIMIT 10;

A room with no bill in the preceding period yields NULL comparisons, rendered as —, never as a fabricated 0.

15. Assumptions recorded by this section

  1. Arrears rows are the aged bills. Report 2's rows are Unpaid bills already past due, with the not-yet-due residual shown as a summary line above the table. This is the only way both halves of D-42 hold at once (§13.3).
  2. Rooms tiles exclude deactivated rooms. rooms_total, rooms_occupied and rooms_vacant all filter is_active = 1, matching D-47's rule that a deactivated room leaves every list except an explicit filter. Against the D-44 seed nothing is deactivated, so 80 / 67 / 13 is reproduced exactly.
  3. A missing rate aborts the whole run. D-17 does not say what happens when no rate row is eligible for a period. Refusing the run with RATE_NOT_FOUND before any write is safer than pricing a utility at zero, and it is the only branch that leaves nothing half-generated.
  4. Report 1's outstanding column reads the stored Unpaid status, so it includes bills that are not yet due. It is a billing summary, not an arrears list; report 2 is the arrears list. This mirrors D-41's outstanding_total and keeps billed − collected = outstanding true on every row.
  5. The single-bill approve is a page POST, not an eighth JSON endpoint (POST /bills/:id/approve), because ADR §6.2 fixes the JSON surface at seven endpoints and POST-Redirect-GET is the page default. It calls the same approveBills() service.
  6. Receipt-number formatting is the one money-adjacent operation performed in JavaScript — String(seq).padStart(6, '0') is string work, not arithmetic, and does not breach D-16.
  7. Nothing here reintroduces a PRD §24 exclusion. No rent, no lease contract, no proration, no gateway, no slip, no QR, no automatic meter, no AI. Payment is cash at the counter; the only automation is the reminder job and the LINE messages.
