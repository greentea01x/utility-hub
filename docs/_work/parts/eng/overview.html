System Overview & Requirements

Juristic Platform is a server-rendered web application that lets the juristic person of a single apartment building charge each room for water, electricity and the common area fee, collect the money in cash at the office counter, issue a numbered receipt, and keep every tenant informed through a LINE Official Account. It does not charge rent and it holds no lease data (PRD §24, D-05).

This section fixes what the system must do and how well, in terms a sibling section can implement, test or draw against without asking a question. Names, stack, table names, enum values and conventions are taken from ADR-001 and are not restated here where the ADR already binds them; every rule that comes from the product decision log cites its decision id (D-xx).

1.1 Purpose and operating model

The building runs on a monthly rhythm. Staff walk the meters in the first days of a month, the office generates and approves that month's bills, LINE delivers them, tenants pay cash at the counter, and the Dashboard and reports explain the month afterwards. One calendar month is one billing period — a plain YYYY-MM string, with no open/close state machine anywhere in the system (D-11).

Product name
Juristic Platform (English identifier). The running app's header shows the apartment name from Settings; the receipt letterhead carries only the apartment's own identity (D-01).
Scale
One property, one building, 80–300 rooms (D-04). The seeded demo is 80 rooms — 67 Occupied, 13 Vacant (D-44).
Users
Two staffed roles (admin, staff) plus tenants who never log in (D-36).
Money
THB only, DECIMAL only, cash only. 1,790.00 in tables and on the receipt, 1,790 บาท in LINE and sentence text (D-03, D-16, D-24).
Time
Asia/Bangkok everywhere, Gregorian years (2026), ISO 8601 in every payload (D-03).
Language
Thai UI, English identifiers. No i18n framework, no language switcher (D-02).
Delivery target
3–4 students, one semester, free-tier hosting, one deployable process, zero build steps (ADR §1, D-43).

The system's reason to exist is the arithmetic and the audit trail around it. Everything else is a screen over it:

units = current_reading − previous_reading  ·  amount = ROUND(quantity × unit_price, 2)  ·  total = SUM(three bill items)

Worked once, with the numbers this document set uses everywhere (PRD §28, D-44):

ค่าน้ำ   1,260 − 1,250 = 10 หน่วย × 18.00 = 180.00
ค่าไฟ   5,350 − 5,280 = 70 หน่วย × 8.00 = 560.00
ค่าส่วนกลาง   30.00 ตร.ม. × 35.00 = 1,050.00
ยอดรวม   180.00 + 560.00 + 1,050.00 = 1,790.00 บาท  ·  ห้อง 205  ·  กำหนดชำระ 5 ก.ย. 2026
Binding: the arithmetic is reproducible, the calendar is not

Every document uses the PRD §28 values verbatim in examples — including 5 ก.ย. 2026, 3 ก.ย. 2026 and REC-202609-000852. The live demo reproduces the arithmetic (10 หน่วย, 70 หน่วย, 180, 560, 1,050, 1,790), never the dates, because the due date, the Overdue display and the receipt number are all functions of the run date (D-20, D-21, D-27, D-44). PRD §16's 18,500 and 62,500 and PRD §19's 35 ตร.ม. row are illustrative and are never used as expected values.

One place a decision overrides literal PRD text

PRD §12 says เจ้าหน้าที่ presses Confirm Cash Payment. That contradicts PRD §4, which grants รับชำระเงิน and ออกใบเสร็จ to Admin only. §4 wins: the counter is operated by an Admin login (D-36, assumption A-13.7). Every document flags this; the test plan asserts a 403 for Staff on POST /payments.

1.9 Assumptions recorded by this section

Authored here, not inherited
  1. The 80–300 room range comes from the project brief, not from the PRD; the PRD and the seed both describe an 80-room building. Nothing in the schema or the queries is room-count dependent, so the range costs nothing — but the LINE allowance ceiling of NFR-02 is real and is stated rather than hidden.
  2. NFR-23's 10-minute recovery target is authored. The decision log commits to a committed seed and periodic dumps (D-43, D-44) but names no recovery time; ten minutes is what a mysql < seed.sql against a local instance actually takes, and it is the number the runbook should be held to.
  3. NFR-25 (accessibility basics) is authored. No decision covers keyboard access or non-colour status conveyance; both are cheap here because the UI is server-rendered HTML with real form controls, and dropping them would be a regression no later section could recover.
  4. NFR-26 (maintainability) restates ADR §1 and §6.9 as a committed requirement so the test plan has an ID to reference.
  5. The FR / NFR identifier scheme (FR-01…FR-48, NFR-01…NFR-26) is introduced by this section. FR-01…FR-30 are pinned to PRD §18's order and must never be renumbered; FR-31 and above may be appended to but not reordered, because the test plan and the traceability matrix key on these ids.
  6. The nine cycle phase names of §1.4 — Reading round, Generation, Approval, Delivery, Reminders, Collection, Receipt, Settlement, Reporting — are authored labels for grouping requirements. They are documentation vocabulary only: no column, route or enum uses them.
Two places where a document must not "tidy up" what looks like an inconsistency
  • previous_period is VARCHAR(8), not VARCHAR(7), because it holds the literal 'baseline' as well as a YYYY-MM period.
  • Enum casing is mixed on purpose — Draft/Unpaid/Paid and Active/Inactive are capitalised, admin/staff, water/electric/common and queued/sent/failed/skipped_no_line are lowercase, and notification types are upper snake. Test selectors and template keys already depend on it.
