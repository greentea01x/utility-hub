LINE Official Account Integration & Notifications

This section specifies every part of the system that talks to LINE: the channel and its credentials, the inbound webhook, the one-time-code account linking flow, the seven Thai message templates, the send path with its retry and idempotency guarantees, the daily scheduler, and how all of it is tested without spending the free plan's monthly allowance. It is binding on routes/line.js, routes/internal.js, services/notify.js, services/linking.js, services/jobs.js and lib/templates.js.

The one architectural rule of this section: money state commits first, messages leave afterwards, outside the transaction (D-30). A LINE outage cannot roll back an approval or a payment, and no route waits on LINE inside a database transaction.

2. Official Account, channel and credentials

2.1 One-time console setup

  1. Create a LINE Business ID for the team (a shared account, not a student's personal ID — the credentials outlive the semester).
  2. In the LINE Official Account Manager, create the OA. Display name is the apartment name from Settings (demo seed: ศุภาลัย เรสซิเดนซ์) — never the software name (D-01).
  3. In the LINE Developers Console, create a provider and, under it, a Messaging API channel linked to that OA. Do this twice: one production channel and one (dev) channel — see §7.4.
  4. Copy the Channel secret (Basic settings) and issue a long-lived Channel access token (Messaging API tab). Both go into environment variables and a password-protected team note, never into the repository (D-43).
  5. Set the webhook URL, enable Use webhook, press Verify, and set the response-mode and reply settings exactly as in the table below.
  6. Download the OA's QR code image and place it on the printable linking slip (§4.2).

3. The webhook endpoint

POST /line/webhook is one of the three routes that bypass the session middleware chain (ADR §2.1). It authenticates with X-Line-Signature and nothing else — no session, no CSRF token, no rate limiter.

ConditionResponseBodySide effect
Valid signature200emptyEvents processed after the response is written
Missing or bad signature401emptyNothing. One warn log line with the source IP, never the body
Body is not JSON but the signature is valid200emptyOne error log line; no events processed
Console Verify button (events: [], valid signature)200emptyNone — an empty array is a normal, expected request
A handler throws while processingalready 200—Logged; LINE is never told, because LINE disables an endpoint that keeps failing
 
// routes/line.js — mounted BEFORE express.json(), which would consume the raw bytes.
import { validateSignature } from '@line/bot-sdk';

router.post('/line/webhook',
  express.raw({ type: 'application/json', limit: '256kb' }),
  (req, res) => {
    const sig = req.get('x-line-signature') ?? '';
    if (!validateSignature(req.body, process.env.LINE_CHANNEL_SECRET, sig)) {
      log.warn({ evt: 'LINE_BAD_SIGNATURE', ip: req.ip });
      return res.sendStatus(401);                     // no envelope: LINE reads no body
    }
    res.sendStatus(200);                              // ACK FIRST — D-29, D-43
    let events = [];
    try { events = JSON.parse(req.body.toString('utf8')).events ?? []; }
    catch (e) { return log.error({ evt: 'LINE_BAD_JSON', msg: e.message }); }
    setImmediate(() => handleWebhookEvents(events)
      .catch((e) => log.error({ evt: 'LINE_EVENT_FAILED', msg: e.message })));
  });
Do not use the SDK's middleware() helper

@line/bot-sdk's middleware() runs the handlers and only then responds. On a Render free instance a cold start plus two queries can exceed LINE's timeout; repeated timeouts get the webhook disabled, and a disabled webhook silently kills the only channel by which a userId ever arrives (D-29, D-43). Verify the signature by hand, answer 200, work afterwards.

3.1 Local development with ngrok

  1. node --env-file=.env --watch server.js — the app listens on http://localhost:3000.
  2. ngrok http 3000 — copy the https://<random>.ngrok-free.app forwarding URL.
  3. In the (dev) channel only, set the webhook URL to https://<random>.ngrok-free.app/line/webhook and press Verify. Expect Success; a 401 there means LINE_CHANNEL_SECRET belongs to the other channel.
  4. Add the dev OA as a friend from your own phone, then send a link code issued against a seeded tenant.
  5. Inspect the raw request at http://127.0.0.1:4040 (ngrok's own inspector) when a signature check fails — the usual cause is a body parser mounted before the raw parser.
A free ngrok URL changes on every restart

One channel holds exactly one webhook URL, so two students cannot both point the dev channel at their own tunnel. The rule is: whoever is working on linking that day owns the dev channel and re-pastes the URL; everyone else works against LINE_MOCK=1 and the signed-curl fixtures of §7.3, which need no tunnel at all. The same rule appears in the runbook as "re-verify the webhook URL after every deploy and before the demo" (D-43).

4. Account linking

A tenant cannot read their own userId anywhere in the LINE app, so staff cannot type it and no import file can contain it. The only self-service path that uses nothing but the Messaging API is a printed one-time code (D-29). Uniqueness is on the tenant: tenants.id already gives it, so one LINE account may be bound to two Active tenancies — a parent renting two rooms — and every template names the room (ADR A-12).

5. Message catalogue

Seven templates, all plain text, all built from braced placeholders only — no room number, month, amount, date, office hour or apartment name is ever hard-coded (D-31). Every template is one function in lib/templates.js; no message string appears at a call site.

renderTemplate(key, vars) → string // key ∈ BILL | BILL_CORRECTED | PRE_DUE | OVERDUE | PAID | ANNOUNCEMENT | LINK_OK | LINK_FAIL | AUTO_REPLY
Template keys are not notification types

notifications.type has exactly six values: BILL, BILL_CORRECTED, PRE_DUE, OVERDUE, PAID, ANNOUNCEMENT (ADR §3.3). LINK_OK, LINK_FAIL and AUTO_REPLY are reply-only template keys: they are sent with the Reply API, they write no notifications row, and they never appear in the monthly counter (ENG-4).

Money in LINE is written 1,790 บาท — number, space, บาท, trailing .00 dropped, never the ฿ glyph, which renders inconsistently in the LINE client (D-03). Dates use the full Thai month and a Gregorian year (5 กันยายน 2026), never Buddhist Era. A missing placeholder is a thrown error, not an empty string: renderTemplate fails loudly rather than sending ห้อง undefined.

Enqueue is an insert-if-absent that never disturbs an existing row, so approving twice produces no second message:

INSERT INTO notifications
  (type, bill_id, announcement_id, tenant_id, recipient_user_id, status, retry_key, send_date)
SELECT 'BILL', b.id, NULL, b.tenant_id, t.line_user_id,

  FROM bills b JOIN tenants t ON t.id = b.tenant_id

An unlinked tenant is written straight to skipped_no_line at enqueue time, never left queued for a drain that would only discover the same thing.

6.4 Drain, retry and idempotency

Five layers, all in the database, none in process memory (ADR §7.6):

#LayerCloses
1UNIQUE(dedupe_key) on CONCAT_WS(':', type, IFNULL(bill_id,0), IFNULL(announcement_id,0), tenant_id, send_date)Two rows for the same message type, bill and tenant on one day — whatever calls the code. D-30's literal UNIQUE(type, bill_id, announcement_id, tenant_id, send_date) cannot do this: InnoDB treats NULLs as distinct and one of the two id columns is always NULL (ENG-3)
2attempt_countAn endless automatic retry loop. Automatic retries stop at 3; the Admin's manual button is never capped (D-30, D-33)
3X-Line-Retry-Key header carrying notifications.retry_keyA push that succeeded at LINE but whose result was lost before it could be recorded — LINE discards the repeat
4SELECT GET_LOCK('notif_drain', 0), released in a finallyThe approve result screen and the daily job pushing the same rows concurrently. Fallback if the provider blocks it: FOR UPDATE SKIP LOCKED inside the drain transaction
5UNIQUE(job_name, run_date) on job_runsA retrying scheduler running the day twice (D-32)

The drain selection, run under the lock, at most 20 rows per call (D-19):

SELECT id, type, bill_id, announcement_id, tenant_id, recipient_user_id, retry_key, attempt_count
  FROM notifications
 WHERE (status = 'queued' OR (status = 'failed' AND attempt_count < 3))
   AND send_date >= CURDATE() - INTERVAL 7 DAY
 ORDER BY id
 LIMIT 20;

The seven-day window is deliberate: a BILL that has failed every retry for a fortnight must not surprise a tenant who already paid at the counter. Anything older is handed over on paper (D-28) or re-sent by hand.

Retry key reuse — the one rule that is not in the decision log

Automatic retries reuse retry_key, so a push that actually landed is not duplicated. The Admin's manual ส่งแจ้งเตือนอีกครั้ง regenerates it, because the Admin is deliberately asking for a second copy after a tenant said they received nothing — reusing the key there would make the button silently do nothing. Both behaviours honour D-30's "the manual button is never capped".

6.6 Announcements

Announcements do not go through the row-by-row drain, because they exist to be one request. sendAnnouncement() runs after the announcement row is committed:

  1. Resolve the audience: all = every room with an Active tenant; floors = the same, filtered by rooms.floor IN (…) (D-35).
  2. Insert one notifications row per Active tenant in the audience — queued when linked, skipped_no_line when not.
  3. Multicast the rendered text to the distinct linked userIds in chunks of at most 500 (one chunk, always, at this building's size).
  4. Bulk-update that chunk's rows to sent, or to failed with the chunk's http_status.
  5. Return ส่งประกาศถึง {rooms} ห้อง · ส่งสำเร็จ {x} · ไม่มี LINE {y} · ส่งไม่สำเร็จ {z}.

A failed chunk is retried by the daily job as individual pushes — at most 54 messages, one per row, using the ordinary drain path. That is one code path fewer than a chunk-level retry and the quota cost is identical.

7. Scheduler

7.1 Two schedules, deliberately separate

ScheduleCronTargetAuthPurpose
Daily notification job0 9 * * * (timezone Asia/Bangkok in the scheduler UI)POST /internal/jobs/dailyX-Job-TokenPRE_DUE, OVERDUE, drain, retries (D-32, D-33)
Keep-alive ping*/10 * * * *GET /healthzpublicA Render free instance sleeps after ~15 minutes; a once-a-day request keeps it awake for one minute, not one day (D-43)

There is no node-cron and no setInterval anywhere in the process (D-32): an in-process timer never fires on a sleeping instance, which would make the headline automatic-notification feature undemonstrable. If cron-job.org's free tier is unavailable, the documented substitute is a Render Cron Job with the same cron expression and the same header.

Timezone handling, in three places and no others

(1) The scheduler is configured with the Asia/Bangkok timezone, so 0 9 * * * is 09:00 local — never UTC. (2) The process runs with TZ=Asia/Bangkok and every pooled connection runs SET time_zone = '+07:00', so CURDATE() inside the job is the Bangkok date. (3) due_date and send_date are DATE columns read with dateStrings: true, so no JS Date constructor can shift them across a day boundary. Together these are why no date arithmetic happens in JavaScript at all (ADR §6.5, A-5).

The two selections, verbatim in intent (D-33). Both exclude Paid bills and bills whose most recent payment was voided (D-25):

-- PRE_DUE: exactly two days before the due date
SELECT b.id, b.tenant_id FROM bills b

 WHERE b.status = 'Unpaid'
   AND DATEDIFF(CURDATE(), b.due_date) IN (1, 8, 15)
   AND NOT EXISTS ( … same voided-payment clause … );

8.2 Mocking the Messaging API

There is no HTTP mock server and no recorded-cassette library. services/notify.js holds one module-level client and exports a setter:

// services/notify.js
let client = process.env.LINE_MOCK === '1' ? fakeClient() : realClient();
export const setLineClient = (c) => { client = c; };   // unit tests only

// test/helpers/fakeLine.js — 20 lines, the whole mock
export const fakeClient = () => {
  const outbox = [];
  return {
    outbox,
    pushMessage: async (to, msg, key) => { outbox.push({ api: 'push', to, msg, key }); return { status: 200 }; },
    multicast:   async (to, msg, key) => { outbox.push({ api: 'multicast', to, msg, key }); return { status: 200 }; },
    replyMessage: async (token, msg)  => { outbox.push({ api: 'reply', token, msg }); return { status: 200 }; },

Integration tests run the real server with LINE_MOCK=1 and assert on the notifications rows, not on the outbox — the rows are what the Admin screens, the monthly counter and the reports read, so asserting on them tests the thing that ships. A failure is simulated by handing the unit test a client whose pushMessage rejects with a given status. LINE_MOCK=1 is set in CI and in .env; it is never set on Render.

8.3 Simulating webhook events with curl

The signature is base64(HMAC-SHA256(rawBody, channelSecret)). Signing the exact bytes matters: reformatting the JSON changes the signature.

# 1) follow event — registers the userId in line_followers
BODY='{"destination":"Uoa0000000000000000000000000000","events":[{"type":"follow","mode":"active","timestamp":1757203200000,"source":{"type":"user","userId":"Udev0000000000000000000000000001"},"webhookEventId":"01J9FOLLOW","deliveryContext":{"isRedelivery":false},"replyToken":"00000000000000000000000000000000"}]}'
SIG=$(printf '%s' "$BODY" | openssl dgst -sha256 -hmac "$LINE_CHANNEL_SECRET" -binary | base64)
curl -sS -i -X POST http://localhost:3000/line/webhook \
  -H "Content-Type: application/json" -H "X-Line-Signature: $SIG" --data-binary "$BODY"
# expect: HTTP/1.1 200 OK, and one row in line_followers

# 2) message event carrying the link code
BODY='{"destination":"Uoa0000000000000000000000000000","events":[{"type":"message","mode":"active","timestamp":1757203260000,"source":{"type":"user","userId":"Udev0000000000000000000000000001"},"webhookEventId":"01J9MSG","deliveryContext":{"isRedelivery":false},"replyToken":"00000000000000000000000000000001","message":{"id":"1","type":"text","quoteToken":"q1","text":"K7QM4P"}}]}'
SIG=$(printf '%s' "$BODY" | openssl dgst -sha256 -hmac "$LINE_CHANNEL_SECRET" -binary | base64)
curl -sS -i -X POST http://localhost:3000/line/webhook \
  -H "Content-Type: application/json" -H "X-Line-Signature: $SIG" --data-binary "$BODY"
# expect: 200, tenants.line_user_id set, link_codes.used_at stamped, audit row TENANT_LINE_LINK

# 3) tampered signature
curl -sS -i -X POST http://localhost:3000/line/webhook \
  -H "Content-Type: application/json" -H "X-Line-Signature: bm90LWEtc2lnbmF0dXJl" --data-binary "$BODY"
# expect: 401, and nothing written

With LINE_MOCK=1 the reply token above is never sent anywhere, so the fabricated value is harmless. Against the real dev channel a reply token is single-use and expires in about a minute, so replies to a hand-made token fail with 400 — the binding still happens, which is the part under test.

9. Limitations and recorded assumptions

Carried verbatim from D-05, the items this section owns:

  • (7) No tenant-facing web login — tenants only ever receive LINE messages.
  • (8) No email and no SMS channel.
  • (9) The system cannot tell a delivered LINE message from one silently dropped because the tenant blocked the Official Account — LINE reports both as success.
  • (12) The free plan's 500-message monthly allowance is displayed but never enforced; exhausting it silently stops delivery.

Nothing here reintroduces a PRD §24 exclusion: no mobile app (the tenant's client is LINE itself), no payment gateway, no QR payment, no slip upload, no IoT meter, no AI. The LINE messages are notifications; every payment still happens in cash at the counter.

Assumptions recorded by this section
  1. Flex Messages are out of scope for v1. The brief for this section asked for Flex payloads for the bill and the receipt confirmation; D-31 is binding and says plain text only.
