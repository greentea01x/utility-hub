API Specification

This section is the complete HTTP contract of Juristic Platform: every route, who may call it, what it accepts, what it returns, and every rule that can reject it. It is written against ADR-001 §6.2 (API style and base path), §6.3 (envelope and error format) and §6.8 (validation in four layers); where a rule comes from the product decision log the decision id is cited inline. Every worked example uses the PRD §28 demo: room 205, 30 sqm, water 1,250 → 1,260 = 10 units × 18 THB = 180, electricity 5,280 → 5,350 = 70 units × 8 THB = 560, common area 30 × 35 = 1,050, total 1,790 THB, due 5 Sep 2026, paid 3 Sep 2026, receipt REC-202609-000852.

The shape of this API is fixed by the ADR and is not a REST API

ADR-001 §6.2 and A-11 are binding: server-rendered pages with POST-Redirect-GET are the default, and exactly seven JSON endpoints exist under /api. Adding an eighth is a decision, not a convenience. Consequently this specification documents two request surfaces with one shared set of conventions — HTML routes that accept application/x-www-form-urlencoded and answer with a redirect, and the seven JSON endpoints that exist only where a page must not reload. There is no /api/v1, no JSON CRUD for rooms, tenants or users, and no GET /api/me. Where this section shows "request/response" for a form route, the request is form fields and the response is a redirect or a re-render — that is the contract an implementer must build.

Session identity — why there is no GET /api/me

The identity of the caller is never fetched; it is already on the page. On successful login the server stores exactly this object and exposes it to every EJS render as currentUser:

req.session.user = {
  "id": 1,
  "username": "admin",
  "display_name": "นิติบุคคล",   // prints as ผู้รับเงิน on the receipt (D-27, D-46)
  "role": "admin"                // "admin" | "staff"
}

Nothing else is kept in the session but the CSRF token and the flash message. A JSON caller that has lost its session gets 401 UNAUTHENTICATED from the same middleware, and the page surface redirects to /login instead. Adding a /api/me endpoint would be an eighth JSON endpoint serving data the server already rendered.

JSON envelope

Every JSON response carries exactly one top-level key — data or error. No response ever carries both, and no endpoint returns a bare array (ADR §6.3).

{ "data": { "period": "2026-09", "created": 1, "updated": 0, "skipped_approved": 0, "missing_readings": 3 } }
{ "error": {
    "code": "READING_BELOW_PREVIOUS",
    "message": "เลขมิเตอร์ปัจจุบันน้อยกว่าเดือนก่อน (1,250) กรุณาตรวจสอบ",
    "fields": { "current_reading": "ต้องไม่น้อยกว่า 1,250" } } }

code is a stable UPPER_SNAKE identifier that tests assert on; message is Thai and is what the user sees; fields is present only on a validation failure and is keyed by the input name, so the API message and the inline form message are the same string produced by the same zod schema (D-40).

Validation error shape

Layer 2 of ADR §6.8 — one zod schema per endpoint, parsed before the handler body runs — produces both payloads below from one definition. Staff saves room 205's water meter as 1,240 against a previous of 1,250:

POST /api/readings          →  422
{ "error": {
    "code": "READING_BELOW_PREVIOUS",
    "message": "เลขมิเตอร์ปัจจุบันน้อยกว่าเดือนก่อน (1,250) กรุณาตรวจสอบ",
    "fields": { "water.current_reading": "ต้องไม่น้อยกว่า 1,250" } } }

The same rule reached through a page form re-renders the form with 200, 1240 still in the input and the identical Thai sentence above it. fields keys are input names, dotted for nested objects, so the client can attach each message to its own input without a lookup table.

Pagination, filters and periods

ConventionRule
Pagination?page=, 1-based, fixed page size 50, applied to /rooms, /tenants, /bills, /announcements and /users. An out-of-range page clamps to the last page rather than 404-ing. The rendered page includes views/partials/pagination.ejs. No JSON endpoint paginates: the only list-shaped JSON response is /api/notifications/drain, capped at one batch by design.
The one exception/readings is never paginated — the floor-grouped reading round must be one continuous page on a phone, and the sticky counter counts the whole period (D-15).
Period?period=YYYY-MM, regex ^\d{4}-(0[1-9]|1[0-2])$. Absent or malformed ⇒ the current calendar month in Asia/Bangkok. There is no periods table and no open/closed state (D-11).
FiltersEnumerated per route and rejected with VALIDATION_FAILED if unknown — never silently ignored.
CSV?format=csv on the four report routes only. Content-Type: text/csv; charset=utf-8, Content-Disposition: attachment; filename="report-arrears-2026-09.csv", UTF-8 BOM so Excel opens Thai correctly (D-42).

Endpoint detail

Login, logout, session

POST /login — body username, password, _csrf.

OutcomeResponse
Credentials valid, user Active303 → /dashboard. The session is regenerated first, so a fixated session id cannot survive login.
Wrong password, unknown username, or Inactive user200, login page re-rendered, username preserved, password cleared, LOGIN_INVALID message. The three cases are indistinguishable to the caller by design.
11th failure from one IP in 15 min429, LOGIN_RATE_LIMITED (D-37)

POST /logout — body _csrf only. Deletes the session row, clears the cookie, 303 → /login. It is a POST, not a GET, so a prefetch or an image tag cannot log a cashier out mid-transaction.

POST /password — body current_password, new_password (min 8), confirm_password, _csrf. Re-hashes at bcrypt cost 10 and keeps the session. This is a change, not a reset: D-37's "no self-service password reset" stands, and a locked-out user is still recovered only by an Admin through POST /users/:id/password.

Users

POST /users — fields username (unique, 3–50, ^[a-z0-9._-]+$), display_name (1–100, printed as ผู้รับเงิน on receipts), role (admin|staff), password (min 8). status is Active on create. Success 303 → /users; duplicate username 409 USERNAME_TAKEN re-rendered inline.

POST /users/:id updates display_name, role and status only. username is immutable — it is the login identity and appears in every audit row. There is no delete: payments.received_by_user_id, meter_readings.recorded_by and rates.created_by reference the row forever, so deactivation is the only removal (D-46). An Admin cannot set their own account Inactive; that attempt returns 422 VALIDATION_FAILED with {"status": "ไม่สามารถปิดใช้งานบัญชีของตนเองได้"}, which is what prevents an empty-admin system.

Tenants CRUD and the LINE link code

POST /tenants — full_name (1–100), phone (^0\d{9}$, e.g. 0812345678), room_id, move_in_date. line_user_id is never accepted from a form — it is filled only by the webhook (D-10, D-29). The insert relies on uq_tenants(active_room_id): a second Active tenant for room 41 is rejected by the database, surfaced as 409 TENANT_ROOM_OCCUPIED, not by a SELECT-then-INSERT race (ENG-1).

POST /tenants/:id/end-tenancy — reason (≥ 10 Thai characters). Blocked with 422 TENANCY_END_BLOCKED unless both conditions of D-08 hold. On success, one transaction sets status='Inactive', writes move_out_date = CURDATE(), clears the three LINE columns, sets rooms.status='Vacant' and writes TENANCY_END with the reason (ENG-5).

POST /tenants/:id/link-code — no body beyond _csrf. Response 303 → /tenants/37/link-code/slip. The generated row:

{ "tenant_id": 37, "code": "K7M2XQ", "expires_at": "2026-09-08 09:14:02", "used_at": null }

Alphabet ABCDEFGHJKLMNPQRSTUVWXYZ23456789 — no O/0/I/1 — 6 characters, 7 days, single use (D-29). Issuing a new code does not invalidate an unused earlier one; both remain valid until used or expired, because a tenant who has already been handed a slip must not be silently cut off.

Meter readings — the previous reading is resolved server-side, with no endpoint

There is deliberately no "get previous reading" call. The /readings page renders Previous as read-only text, and POST /api/readings echoes the value it actually used. One query serves both (ADR §7.1):

SELECT current_reading, period
  FROM meter_readings

200

One call pushes at most 20 personalised messages, or one multicast chunk of at most 500 announcement recipients (D-34). lock is "acquired" or "busy": when GET_LOCK('notif_drain', 0) fails, the call returns busy with zero counts and the client waits one second and retries — that is what stops the approve screen and the 09:00 job pushing the same rows (ADR §7.6). Layer 4 is the one that still holds under a race

Eleven unique keys, three generated columns and three CHECKs carry the guarantees above through a double-click, a forgotten handler check and a hand-typed UPDATE: uq_readings(room_id, period, utility_type), uq_bills(room_id, period), uq_bill_items(bill_id, item_type), uq_payments(active_bill_id), uq_tenants(active_room_id), uq_receipts(payment_id), uq_receipts(receipt_no), uq_notifications(dedupe_key), uq_job_runs(job_name, run_date), uq_rates(utility_type, effective_from), uq_rooms(room_code). Layers 1–3 exist to give a human a good Thai message; layer 4 exists to make the wrong number impossible (ADR A-10). None of these may be cut.

Assumptions recorded by this section

  1. Form routes are the API for CRUD. Rooms, tenants, users, settings, payments, revert, void and announcements have no JSON endpoints, because ADR §6.2 fixes the JSON surface at seven endpoints. Where this section shows a "request body" for those, it is form-encoded and the response is a 303 or a re-render.
  2. No GET /api/me. Identity is req.session.user, rendered into the page. A JSON caller that lost its session learns so from 401 UNAUTHENTICATED.
  3. expected_total on POST /payments is added as a staleness guard, not as an amount input. The stored amount is still copied from bills.total in SQL (D-24); the field only turns a stale screen into a 409 instead of a wrong receipt.
  4. Single approve reuses the bulk endpoint. Bill Detail's button posts {"bill_ids":[118]} to POST /api/bills/approve, so there is one approval code path and one set of guards rather than two.
  5. Recalculating Draft bills reuses POST /api/bills/generate — a run already recalculates every Draft bill of the period in place (D-18), so D-17's คำนวณบิลฉบับร่างใหม่ button needs no endpoint of its own.
  6. The PAID message is drained by the receipt page calling POST /api/notifications/drain once on load; the daily job would deliver it anyway. No per-message send endpoint exists.
  7. A webhook text message is treated as a code attempt when, after trimming and upper-casing, it is exactly 6 characters drawn from the D-29 alphabet. Anything else gets the fixed auto-reply. Without this test the system cannot distinguish a mistyped code from small talk.
  8. D-37's "first login forces a change" is realised as GET/POST /password plus a runbook step and a dashboard banner, not as a forced redirect: the ADR's users table carries no must_change_password column, and inventing one here would contradict the schema section.
  9. Page size 50 and the /readings no-pagination exception are chosen here; the ADR fixes neither. Against the seed (80 rooms, ≤80 bills per period) pagination is reachable only on the all-period bill list.
  10. Announcement drains use multicast chunks of at most 500 recipients per call, while personalised types drain at most 20 rows per call, per D-34's delivery split and ADR §7.6's batch cap.
